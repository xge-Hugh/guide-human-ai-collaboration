## 10. 下一阶段：执行保障机制

本版回答“理想的人机协作应该怎样进行”，尚未回答“怎样使这些行为在真实压力、长任务和跨会话情况下稳定发生”。

### 10.1 已确认的问题

- 人的工作记忆有限，依赖主观记忆维护流程不可靠；
- 文档可能无人阅读、内容过期、互相冲突或流于填表；
- AI 的上下文有限，额外维护流程状态会挤占任务上下文并可能降低工作质量；
- 会话压缩、模型切换和人员交接可能丢失关键状态；
- 提示语、约定和自觉属于软约束，无法稳定保证阶段顺序、退出条件和独立审查；
- 过强门禁又可能制造官僚负担、阻塞应急交付并诱发形式主义。

### 10.2 下一阶段目标

设计一套低摩擦、可观察、可中断、可恢复、按风险调节强度的执行保障机制。它至少需要回答：

1. 五个阶段及其退出条件如何被可靠触发和记录；
2. 如何让独立预测发生在答案暴露之前，同时不阻塞紧急任务；
3. 最小认知包、关键决策、验证债务和学习状态如何跨会话、模型和人员持续；
4. 独立审查怎样在上下文和证据方法上形成真实隔离；
5. 压力模式下哪些环节可以压缩，哪些安全边界不能绕过；
6. 未完成的验证、审查、文档和认知债务如何被自动发现；
7. 如何防止模板化填充、刷指标和形式主义；
8. 机制失效时如何降级、恢复并保留人工接管；
9. 如何收集足够证据评估机制，又不演变为人员监控或心理画像；
10. 如何控制保障机制自身的上下文、维护和使用成本。

### 10.3 本阶段明确不做

本次不预设必须采用：

- 插件或 IDE 扩展；
- Agent 技能、系统提示或单一模型；
- 工作流引擎；
- 数据库、状态服务器或知识图谱；
- PR 门禁或 CI 自动化；
- 聊天机器人或独立应用；
- 复杂评分系统。

下一阶段应先定义保障目标、威胁模型、失败模式和验收标准，再比较人工检查点、结构化状态、工具集成、自动门禁等不同实现手段。

### 10.4 首个试运行：Out.WebApi Batch 重构

`Interfaces/SunWard.Out.WebApi` 增加业务层 Batch 能力作为本工作流的首个真实试运行。以下是任务理解阶段形成的初始验收假设，仍需在实施讨论中校准：

- **业务结果**：既有业务 endpoint 的有效调用链不能因重构失效；新增批量能力能够支持目标业务场景。
- **开发体验**：常见批量 CRUD 调用简洁、容易发现和理解；业务开发者不需要接触 multipart、boundary、Content-ID 等协议细节。
- **结构质量**：公共组织语义与内部传输协议边界清楚；复用已有 Batch/ChangeSet 协议能力，不重复实现转换和发送链路。
- **可维护性**：代码长度和类型数量与真实复杂度相称；不引入无当前需求支撑的 ORM、Planner、Writer、工作流 DSL 或其他预扩展抽象。
- **协议正确性**：普通 Batch 与原子 ChangeSet 的语义、失败结果和事务边界符合 Dataverse Web API 的实际行为及官方约束。
- **工作流有效性**：流程应帮助人理解并审查上述取舍，同时不显著增加阅读、填表和交付阻力；若复杂度没有带来可观察收益，应缩减、重构或否定相应机制。

这里的“优雅”不是单一审美结论，而是对调用便利、表达简洁、边界清楚、复用充分、理解成本和维护成本的综合期待。实施讨论需要把相关部分转化为可观察证据，但不应为了可量化而制造机械指标。

试运行同时观察流程自身，而不预设固定字数、问题数量或时间比例：

- 从提出任务到首次有效行动的时间；
- AI 要求人作出决定的次数及其必要性；
- 人是否出现明显阅读、填表、反复解释或决策疲劳；
- 学习插槽是否阻塞业务主线；
- 流程是否实际减少方向性返工、无依据假设和审查遗漏；
- 人是否产生绕过流程的冲动，以及原因是什么。

这些信号用于发现趋势和修订机制，不用于人员绩效评分。若流程负担持续高于它减少的风险与产生的学习收益，应主动缩减，而不是要求协作者投入更多意志力维持它。

### 10.5 状态载体与上下文压缩观察

当前形成的轻量假设是：影响后续判断的重要状态需要持久化，临时推理和探索过程保留在对话上下文；只有阶段边界、重大决定、风险变化或交接需要时才更新持久化状态，不保存全部聊天流水。

当前所有权已明确为个人资产，不作为 SUNWARD CRM 团队规范。本文暂时借当前仓库完成设计和试运行，不代表最终必须存放在该仓库或由团队共同维护。

持久化位置尚未决定。候选方向至少包括：

- **仓库内**：天然贴近代码、分支、评审和团队上下文，但可能产生临时文档、仓库噪声、敏感信息和生命周期问题；
- **产品专用全局目录**：适合对应产品自动发现，却不天然对其他 AI 产品可见，可能产生迁移、同步和供应商锁定，因此不宜作为跨产品个人规范的唯一权威来源；
- **产品无关的个人全局位置**：适合个人偏好、通用规范和长期学习状态，但仍需解决不同产品的文件访问权限、路径差异、任务关联、发现和加载方式；
- **按所有权拆分的混合方式**：任务与团队事实随仓库保存，个人偏好、跨任务索引或学习状态保存在仓库之外，但需要解决引用、同步和冲突。

位置决策应依据状态由谁拥有、谁需要读取、是否随代码版本变化、隐私和审计要求、生命周期及跨产品可移植性，而不是仅凭某个产品当前默认行为。

当前长对话即将发生的自然上下文压缩作为一次观察点，不主动触发或操纵。压缩后观察 AI 是否：

- 仍能识别当前任务是设计人机协作工作流的执行保障机制，而不是直接实施 Batch；
- 保留“重要状态持久化、临时推理留在对话、位置尚未决定”的最新共识；
- 能从权威文档恢复稳定状态，而不要求人重复已经确认的全部背景；
- 不把候选假设误报为最终决定；
- 能从未决问题继续推进，同时诚实指出无法恢复的临时细节；
- 不因恢复上下文而输出一篇重复历史的长文。

这只是一次案例观察，不能单次证明机制有效；结果应进入复盘，用于改进最小认知包、状态更新时机和恢复流程。

2026-08-09 的首次自然压缩中，AI 保留了当前目标、权威文档位置、最近一次修改失败的状态和最新优先级修正，未要求人重复背景，也未把 Batch 误当成已进入代码实施。恢复仍依赖系统摘要并需要核对外部文档，因此这只是一个正向样本，不足以证明长期稳定性。

同日第二次自然压缩发生在首版实施设计阶段。恢复内容保留了两层 `AGENTS.md` 的实际位置、需要纠正的旧判断、当前文档受众问题和下一步修改方向。这进一步说明“最小持久状态加外部文档核对”具有恢复价值，但仍依赖系统生成摘要；连续两个正向样本不能替代后续对遗漏、冲突和错误恢复的检验。

### 10.6 优先级对齐与价值验证顺序

当前首先要验证的不是跨产品分发能力，而是本工作流能否在不显著拖慢业务交付的前提下：

- 提升人的独立解释、判断和迁移能力；
- 通过可观察贡献改善并校准自我效能，避免无力感或虚高；
- 降低不必要的阅读、理解、填表和决策负担；
- 减少方向性返工、无依据假设、过度抽象和审查遗漏；
- 保持自然、可接受的协作体验。

这些价值假设优先在主要使用的单一产品和真实 Batch 重构中验证。跨产品核心、适配器、同步或远程服务均作为后续候选；只有已有证据表明工作流值得保留，且迁移需求真实出现时，才投入设计。

人的当前重点与 AI 根据技术脉络推导出的“下一步”可能不同。协作中应区分“当前共同目标”“AI 建议的后续方向”和“已推迟事项”。人的最新明确优先级决定当前议程；AI 仍应指出具体风险，但不能以技术上的连续性替代共同决策。

优先级不需要每轮机械确认。只有出现明显分叉、范围扩张、时间预算变化、核心假设被替换或交付物改变时，AI 才用简短重述重新对齐；其余有价值但非当前必要的方向进入待办，不中断主线。

### 10.7 共同航标

长时间讨论中，人和 AI 都可能保留局部内容，却逐渐失去共同目标和下一步。使用可纠正的“共同航标”重新激活方向，而不是依靠双方持续记忆或反复总结全部历史。

默认最小形式为一行：`目标 → 当前阶段 → 下一步`。在确有需要时可补充“已确定、待核实、暂缓”，但同一时刻只突出一个下一步。AI 负责从自然对话中起草，人只在不准确时纠正；推断不得伪装成已确认决定。

航标按事件触发，而不按固定轮数机械弹出。适合触发的事件包括阶段转换、明显话题分叉、中断后恢复、上下文压缩、AI 对当前方向置信度下降，以及不可逆或高影响行动之前。日常推进只报告发生变化的部分，避免把航标扩张成会议纪要、待办仓库或第二套项目管理系统。

未完成主线中出现灵感或旁支时，AI 应判断它是在补充还是替换当前议程。补充内容只在对话中保存轻量返回点，处理完后主动恢复原主线；只有人的新表达真实改变目标、优先级或交付物时，才更新共同下一步。不能因近期内容更显著而静默遗忘未闭合事项，也不能要求人负责提醒“说完后回去”。

试运行进一步暴露：临时旁支会自然成长为独立任务。人机协作规范最初由 Batch 讨论引出，后来已经形成自己的文档、Skill 实施和连续下一步，却没有自己的任务状态；恢复时只有 Batch 状态可见，容易把试点样本误认为当前主线。改进重点不是继续增加跨 session 特判，而是在旁支形成独立目标、持久产物和连续行动后，于自然检查点把它晋升为独立任务。多个任务可以同时活动，当前任务仍由人的表达和对话中的共同下一步确定，状态只负责恢复各自的位置。

上下文责任是双向的：人通过自然表达和必要状态帮助 AI 理解当前任务，AI 在请求判断、恢复或切换任务时，也要向人提供支持当前行动所需的最小上下文。任务状态和完整文档主要承担 AI 的可恢复上下文；即时摘要、代表性例子、主要权衡和明确交接则承担人的可理解上下文。双方都不应被迫从不完整线索猜测对方正在做什么。

该机制的有效性不以“展示过摘要”为证据，而观察它是否在保持低打扰的同时，帮助双方更快、更准确地识别当前目标和下一步，并减少重复询问、错误假设与方向性返工。

### 10.8 首版保障栈与收益优先

当前候选保障栈采用互补分工，而不是在 `AGENTS.md` 与 Skill 之间二选一：

- `AGENTS.md` 只保留少数常驻底线和 Skill 启动条件。它是比按需 Skill 更稳定的指令约束，但仍属于模型可偏离的软约束，不冒充确定性门禁；
- Skill 承载分阶段工作方法、交互判断和资源路由，通过渐进披露按需读取规范、示例和学习材料；
- 复杂任务以任务文件夹为持久化单元；小型机器可读状态只保存协作控制、唯一下一步和权威文档引用，任务目标、不变量、设计与学习证据按需进入对应文档；
- 脚本只负责格式校验、冲突检测、状态渲染等确定性工作；
- Hook 只在压缩和恢复等生命周期节点调用脚本、校验并重新注入最小状态，不自动改写语义共识。

首版不追求机制齐全，优先实现收益高、容易观察、能够快速产生正反馈的部分：自然表达中的目标与不变量提取、共同航标、低负担的阶段回顾，以及人的关键判断和贡献留痕。只有真实试运行反复暴露某类状态遗漏或恢复失败，才增加相应脚本、Hook 或门禁。

### 10.9 社区参考与自行设计边界

首版不从零发明规则路由、Skill 渐进披露、文件化状态、阶段产物和上下文恢复，也不整套照搬任一社区框架。采用“先以本工作流目标建立判断标准，再抽取候选机制，最后在真实任务中逐项验证”的顺序。

现有方案主要优化 Agent 的软件交付可靠性；人的独立判断、自我效能、认知负载、自然表达和脚手架撤除仍是本工作流需要自行设计和验证的核心。详细候选、反例和取舍见 [人机协作保障机制参考研究](../human-ai-collaboration-reference-study.md)。

当前探索已经覆盖首版需要的主要机制类别，达到阶段退出条件。后续只对实施或试运行中出现的具体未知定向研究，不用项目数量和方法论完整度推迟试运行。

这项原则适用于整个工作流，而非只用于保障系统选型。承重、陌生或高风险问题先进行轻量先例勘察：任务理解看领域定义和真实事故，实施讨论看仓库先例与官方架构，编码看既有惯例和官方 API，审查看成熟审查/验证方法，复盘看 AAR、debrief 与无责事后分析。每次明确“借鉴、适配、自研/舍弃”，并以当前不变量和证据裁剪；低风险熟悉任务不强制研究。
