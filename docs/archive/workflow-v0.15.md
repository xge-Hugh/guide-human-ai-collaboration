# 人机协同研发工作流

> 状态：草案
>
> 版本：v0.15
>
> 最近更新：2026-08-09
>
> 适用状态：待真实任务试运行与校准
>
> 下一阶段：设计执行保障机制。本版只定义工作方法、判断标准和失败边界，不预设具体技术方案。

## 1. 目标与适用范围

本文定义一套面向长期研发活动的人机协同工作流。它不以“让 AI 尽可能多地完成工作”为唯一目标，而是同时追求：

- 交付结果正确、稳定、可维护、可追溯；
- 人保有问题定义、独立判断、取舍、验证和最终决策能力；
- AI 的解释和行动与任务风险、人的认知状态、学习目标及时间压力匹配；
- 单次任务能够形成可迁移的人的能力与可复用的团队知识；
- 流程成本与任务价值相称，避免文档和仪式本身成为负担。

本文适用于需求分析、缺陷修复、代码实现、重构、技术设计、代码审查、故障处置和知识传递。低风险、机械性任务可以压缩流程，但不能伪造理解、验证或独立审查。

本文不规定具体模型、IDE、插件、自动化平台或工作流引擎，也不把“使用了 AI”本身视为质量、能力或效率的证据。

## 2. 基本原则

1. **人拥有目的和关键决策权**：人确认任务目的、范围、关键取舍、风险接受和最终验收；AI 负责提供事实、分析、实现和反例，但不能以流畅回答取代人的理解。
2. **保留独立认知活动**：在会改变方向的关键节点，人应尽量在看到 AI 完整结论前留下预测、疑问或初始判断，使 AI 的答案成为比较对象，而不是单纯消费对象。
3. **证据优先于信心**：看懂、解释、预测、执行和迁移是不同层次；任务成功、个人独立能力和人机协作能力也必须分别判断。
4. **先从正确抽象层开始**：先明确目的、行为和约束，再进入架构、代码和底层原理；只有当更深细节会改变结论时才继续下探。
5. **风险决定流程强度**：变更影响、可逆性、不确定性、人的熟悉程度和时间压力共同决定讨论、验证、审查和文档深度。
6. **表示形式服务于信息结构**：文字、表格、流程图、代码、示例、截图或视频按问题性质选择；多媒体不是越多越好。
7. **小批量闭环**：尽早形成“理解—预测—实施—验证—修正”的短循环，发现方向错误时及时回退，而不是用局部补丁掩盖根因。
8. **压力可以压缩形式，不能取消底线**：紧急情况下可以减少解释、文档和学习活动，但不可逆操作、重大假设、关键证据及事后债务必须保留。
9. **学习服务于真实能力**：学习插槽必须来自真实任务并能获得反馈；不以观看、参与时长、提示词数量或 AI 产出数量代替能力证据。
10. **机制约束优于主观记忆**：人的工作记忆、AI 上下文和软性约定都不可靠；本工作流最终需要低摩擦、可观察、可恢复的执行保障机制。
11. **后台结构化、前台自然交流**：工作流主要约束 AI 的组织和判断，不把结构成本转嫁为人的问卷；默认使用最小充分回答，一轮只推进一个主要问题，并允许人随时混合表达、联想和改变关注点。
12. **充分即停止，轻量性是一级不变量**：任务理解和风险收集不追求穷尽；当信息已经足以安全推进，就进入下一阶段。流程增加的时间、注意力和维护成本必须与减少的风险和产生的学习收益相称。
13. **时间用于调度和诊断，不用于制造压力**：有真实期限时为阶段预留预算和检查点，优先保护实施、验证及交付缓冲；时间经过本身不等于失败，只有缺少状态变化和新证据时才触发支架调整。可见倒计时默认关闭。
14. **消除仪式性摩擦，保留建设性对抗**：AI 应从自然表达中提取任务要素，并按风险决定是否需要确认；不能为追求顺从而隐藏重要异议，也不能用流程、术语或泛化风险制造无助于判断的阻力。
15. **冲突必须解决，但只升级真正的冲突**：AI 应先判断新旧说法是否互斥、是否处于同一抽象层，再把无法自动消解且会影响方向的部分交给人；不能沉默选边，也不能把所有差异都升级成正式裁决。
16. **技术上连续不等于优先级正确**：AI 提出的“下一步”只是建议，不能自动成为共同议程。应优先验证任务的核心价值假设，避免被跨产品、自动化或其他有趣但非当前必要的技术问题带偏。
17. **独立判断与先例互补**：先形成当前问题、预测或判断标准，再寻找相似实例和成熟模式作为比较对象。先例用于降低从抽象到具体的门槛、暴露可复用结构与失败模式，不能以流行度或表面相似代替当前任务的证据和取舍。

## 3. 角色与责任

| 角色 | 主要责任 |
| --- | --- |
| 人类负责人（Owner） | 明确目的、范围和成功标准；作出关键取舍；接受风险；选择学习深度；最终验收 |
| 探索者（Explorer） | 收集代码、规范、环境和历史事实；区分事实、推断与未知；不代替负责人作架构决策 |
| 思考者（Thinker） | 建立心智模型；提出方案、因果关系、反例、权衡和风险；不以设计代替事实验证 |
| 实施者（Builder） | 按确认方案完成最小必要变更；暴露假设和偏差；保存相称的验证证据 |
| 独立审查者（Reviewer） | 从任务目的和原始证据重新建立预期，再审查方案、代码和验证；不直接继承实施者结论 |
| 独立验证者（Verifier） | 在高风险任务中通过不同方法验证关键断言，例如规范核对、运行证据或反例实验 |
| 流程维护者 | 维护模板、文档路由和试运行反馈；不代替任务负责人作业务或技术决策 |

同一参与者可以承担多个角色，但独立审查必须在上下文、输入顺序或验证方法上形成实质隔离，不能只是实施者换一种措辞进行自我复述。

## 4. 抽象层级与人的掌握要求

### 4.1 抽象层级

| 层级 | 核心问题 |
| --- | --- |
| L0 结果层 | 最终要得到什么，什么算完成？ |
| L1 行为层 | 输入、输出、规则、不变量和失败表现是什么？ |
| L2 边界层 | 模块、接口、数据、状态和依赖如何协作？ |
| L3 实现层 | 算法、控制流、代码结构和 API 如何实现？ |
| L4 原理层 | SDK、协议、数据库、运行时或硬件为什么这样工作？ |

各阶段默认深度：

- 任务理解：L0—L1，必要时到 L2；
- 实施讨论：L1—L2，影响取舍时到 L3；
- 代码实施：L2—L3；
- 故障定位：依据证据按需下潜到 L4；
- 独立审查：重新覆盖 L0—L3，高风险点按需到 L4；
- 复盘沉淀：回升到 L0—L2，记录真正影响维护的底层结论。

每次明显下潜时，AI 应说明下潜理由。下潜结束后应进行“抽象回收”，把底层事实重新表达成上层可以操作、判断和维护的规则。

理解不要求递归掌握所有下层机制。人的掌握深度应与其在当前任务中的决策责任和学习目标匹配，而不是与代码的重要程度机械绑定。例如，负责人可以在 L1—L2 达到独立判断，却把 L3 实现交给 AI；只有当 L3 细节会改变其取舍、验证或长期维护责任时，才需要继续下探。

人的自然表达不要求一次只处于一个抽象层。一次回答可以同时包含业务目标、行为要求、质量期待和实现偏好，这通常是正常思考而不是表达错误。AI 应先保留完整原意，再在后台拆分层次、标记关系；只有不同层次之间发生冲突、遗漏会改变方向，或某项偏好被误当作硬约束时，才请求人澄清。不能要求人先学会架构分类，才有资格描述问题。

### 4.2 可观察掌握层次

| 层次 | 可观察表现 |
| --- | --- |
| M0 接触 | 看过术语或答案，但不能稳定复述 |
| M1 识别 | 能从实例或选项中识别概念和常见模式 |
| M2 解释 | 能用自己的话解释目的、关系、约束和不变量 |
| M3 预测 | 面对条件变化，能预测结果并说明理由 |
| M4 独立执行 | 能独立实现、调试、验证或完成相应操作 |
| M5 迁移与审查 | 能迁移到新场景、发现边界并审查他人方案 |

M0—M5 描述的是“某人在某个领域、某种情境和某个抽象层上的当前证据”，不是永久等级或身份标签。不同能力可以处于不同层次；高压力和陌生环境也可能暂时降低表现。

业务目的、关键不变量和风险取舍通常至少需要负责人在相应抽象层达到 M2—M3。是否需要达到 M4，由其是否亲自实施、排障或长期承担该实现层责任决定。

## 5. 五阶段闭环

### 5.1 阶段一：任务理解

**目的**

确认为什么做、要改变什么、什么算完成、什么不能破坏，并建立足以继续讨论的最小心智模型。

**输入**

- 原始需求、问题现象或故障信息；
- 已知上下文、限制和已有证据；
- 人当前的理解、预测、疑问或担忧。

**主要活动**

- 区分目的、手段、事实、推断和未知；
- 人在看到完整答案前尽量留下初始预测或最担心的失败；
- 建立范围内、范围外事项和业务不变量；
- 对陌生主题提供最小认知包，而不是从底层解释一切；
- 仅在需要调节解释或学习深度时使用低摩擦诊断。

**最小产物**

- 任务目的和当前问题；
- 基础业务场景；
- 范围、非目标和关键不变量；
- 成功与失败的可观察标准；
- 已知未知项及风险初判；
- 人的初始预测或当前疑问。

简单任务可以在对话中完成；中高风险任务应形成任务文档或工作包。

**退出条件**

- 人能用自己的话解释为什么做、做什么和什么不能破坏；
- 成功与失败可观察；
- 尚未解决的歧义不会根本改变后续方案；
- 协调者明确哪些内容是事实，哪些仍是假设。

退出判断采用“足以安全推进”，而不是“所有问题已经回答”。剩余未知可以被显式记录，并在真正影响方案或风险时再展开；风险目录和模板不能被当作必须逐项完成的访谈清单。

**主责**

AI 起草和澄清，人确认目的、范围和验收。

### 5.2 阶段二：实施讨论

**目的**

确认怎样以正确、稳定且不过度的方式完成任务，使人能够控制方案粒度和关键取舍，而不是控制每一行代码。

**输入**

- 已确认的任务目的、范围和不变量；
- 相关代码事实、规范和历史约束；
- 人的初始预测。

**主要活动**

- 建立现状与目标调用链或因果链；
- 说明首选方案、可行替代方案和拒绝理由；
- 明确领域模型、架构边界、接口、数据和错误语义；
- 识别事务、并发、幂等、性能、N+1、安全等与任务相关的技术概念；
- 让风险与验证方式一一对应；
- 预留学习插槽并明确所有权；
- 明确实施期间允许的命令和验证权限。

**产物**

- 实施文档或工作包中的实施章节；
- 关键因果、不变量和接口变化；
- 影响范围、实施步骤和验证计划；
- 明确不做事项；
- 学习插槽和独立审查策略。

**退出条件**

- 人能解释为什么该方案足以达成目标；
- 人能提出或理解主要反例与取舍；
- 高风险假设具有验证方法或被显式接受；
- 方案粒度已经足以实施，但没有提前设计无真实需求的扩展点。

**主责**

AI 负责技术方案与证据，人负责业务、架构取舍和风险接受。

### 5.3 阶段三：代码实施

**目的**

按已确认方向完成最小必要变更，保持主线交付，并按需为人的定向学习提供真实练习。

**输入**

- 已确认的实施方案；
- 不变量、风险和验证计划；
- 学习插槽及文件或符号所有权。

**主要活动**

- 以可解释、可检查、可回退的小批量变更推进；
- AI 标示重要假设、影响点和未验证项；
- 人根据学习插槽参与选择、填空、局部代码或完整函数；
- 插槽交给人后，AI 不修改相同文件或符号，直到明确交还；
- 发现需求或设计错误时返回阶段一或阶段二；
- 记录实际实现相对实施文档的偏差及原因。

**产物**

- 最小范围的代码或配置变更；
- 变更说明和方案偏差；
- 已取得的静态或运行证据；
- 未验证事项、剩余风险和后续债务。

**退出条件**

- 请求范围已实现，没有静默扩大；
- 关键不变量未被破坏；
- 计划内且已获授权的验证已经完成；
- 未运行的编译、测试或环境验证被诚实标记为未执行；
- 人能在其承担的抽象层解释关键行为和失败模式。

**主责**

Builder 主责实现，人按学习插槽和关键决策参与。

### 5.4 阶段四：独立审查

**目的**

从实施过程之外重新验证任务、设计、代码和证据，降低实施者自审的同源偏差。

**输入**

- 原始任务文档；
- 实施文档；
- 最终差异；
- 验证证据和剩余风险。

**主要活动**

1. 实施结束先区分 Builder 自检与独立审查，向人说明 Reviewer/隔离方式；协作方式会改变时由人选择，不静默跨阶段长时间执行；
2. Reviewer 先读任务目的，独立写出预期行为、风险和反例；
3. 再读实施方案和最终差异，判断方向是否足以达成目的；
4. 按“变化—失效模式—业务后果—证据缺口”选择最有判别力的证据；
5. Builder 的解释只用于澄清，不能作为正确性证据；
6. 高风险任务增加不同方法的第二条验证链；
7. 人参与审查时，AI 按职责或风险拆分代码，提供目的、变化路径、代表性切片、已知权衡和具体判断，不要求人直接读完大差异。

审查至少覆盖：

- 目标正确性：是否真的解决了任务；
- 设计一致性：是否符合确认的不变量和边界；
- 代码质量：是否简单、可维护、无重复和无关改动；
- 验证充分性：证据是否支持结论，未验证项是否被准确表达。

性能、N+1、并发、安全、兼容性和可观测性按变化路径与业务影响选择。静态怀疑先形成可验证假设；没有代表性测量或实际业务收益时，不做无关优化。测试代码本身也是被审查对象，数量和覆盖率不能代替其判别力。

**产物**

- 阻断项、建议项和残余风险；
- 修复后的复审结论；
- 高风险断言的交叉验证证据。

**退出条件**

- 阻断项已关闭，或由有权负责人显式接受；
- 高风险交叉验证已完成；
- 人接受残余风险；
- 未执行的验证没有被表述为已通过。

**主责**

Reviewer 主导审查，Builder 修复，人最终验收。

### 5.5 阶段五：复盘沉淀

**目的**

回顾整个协作过程，结算任务结果、认知变化和可复用资产，使单次任务形成真正闭环。

**输入**

- 任务、方案、代码、验证和审查结果；
- 初始预测与实际证据；
- 实施中的偏差、摩擦和意外发现。

**主要活动**

- AI 先用事实简述原本预期和实际发生，不用文档链接替代即时说明；
- 吸收人已经表达的故事、感受和判断，只对关键缺口提出一个开放问题；
- 比较预测与实际，说明模型为何正确或错误；
- 观察任务结果、人与 AI 的贡献和失误、工作流表现，以及限制表现的环境/工具/知识与高杠杆改进；
- 有学习目标时结算独立能力、协作能力和可迁移练习，不把“看懂代码”记为掌握；
- 共同选择极少数下一次可观察改进，并将长期有效的信息路由到正确文档。

**产物**

- 结算卡；
- 必要的决策记录、开发文档或运行手册更新；
- 技术债务、认知债务和流程债务；
- 下一次协作的推荐起点。

**退出条件**

- 结果、证据、偏差和剩余风险已经结算；
- 人已经参与复盘或明确选择跳过；开启学习目标时，人明确现在能独立完成什么、尚无什么证据；
- 长期有效的信息已进入正确载体；
- 无价值的过程材料没有被误当作永久知识。

**主责**

人确认结算，AI 帮助归纳但不得虚构人的掌握程度，流程维护者收集跨任务模式。

## 6. 横切认知机制

### 6.1 独立预测与主动思考

在关键答案、方案或根因被完整揭示前，人尽量留下：

- 当前认为会发生什么；
- 判断依据；
- 最大不确定性；
- 什么证据会改变判断。

预测的目的是暴露当前图式并支持后续比较，不是追责或考试。它应集中在会改变方向的节点，不能覆盖命名、格式和机械实现等低价值选择。

如果用户已经主动提出判断、约束或反例，AI 应直接对其进行比较和校准，不得机械地要求再次预测。高压力情况下，预测可以压缩为一次选择；应急情况下可由 AI 记录临时假设并先执行安全、可逆的动作，稳定后补做比较。

Prompt 的长短不是独立思考或能力的可靠指标。简短表达可能来自熟悉、压力、疲劳或不知道从何问起，AI 只能把它作为弱信号。

### 6.2 压力模式

| 模式 | 适用情境 | 人的参与 | AI 行为 |
| --- | --- | --- | --- |
| 标准 | 常规研发 | 预测、取舍、学习插槽 | 解释与实施并行 |
| 加速 | 时间紧、风险可控 | 每轮一个关键决定 | 压缩背景，先做可逆步骤 |
| 应急 | 生产事故或重大阻断 | 只确认不可逆和高风险动作 | 接管主线，持续报告关键证据 |

模式切换必须被显式报告并允许用户纠正。降低启动摩擦的方法包括：

- 开放题改为少量选项；
- 完整描述改为补一个关键空白；
- 每轮只要求一个决定；
- 给出安全、可撤销的默认值；
- 非关键问题采用显式、可纠正的假设；
- 优先产生真实证据和控制感。

应急期间跳过的设计解释、审查、验证或学习形成可追踪债务。退出应急后，优先偿还会影响维护和下一步决策的部分。

#### 时间预算、检查点与停滞信号

时间机制属于工作流的后台调度层，不新增每轮都要执行的计时仪式：

| 机制 | 默认性质 | 作用 |
| --- | --- | --- |
| 阶段预算 | 软约束 | 避免代码实施前过度消耗时间，保护最小交付和最终验证 |
| 检查点 | 调节机制 | 在关键产物、依赖或风险变化时重新判断投入方向 |
| 停滞信号 | 诊断信号 | 识别题目、支架、依赖或路径可能不合适 |
| 外部截止 | 真实硬约束 | 表达发布窗口、提交期限、安全或他人依赖等不可移动边界 |
| 可见倒计时 | 强提醒，默认关闭 | 仅在用户主动要求或临近真实操作窗口时使用 |

有明确期限的任务，应先确认最小交付物、实施需要、不可省略的验证和提交准备，再把剩余预算分配给理解、探索和方案讨论。某阶段出现高价值新证据可以延长，但必须同步缩减低优先级范围、升级协助或重新报告交付风险，不能只把压力推向最后。

检查点关注状态变化，而不是机械的等间隔提醒：

- 是否产生了新证据、中间产物或新的可行策略；
- 关键不确定性和剩余工作是否在下降；
- 当前投入是否仍能减少返工、交付风险或学习障碍；
- 是否开始侵占必要的实施、验证和交付缓冲。

“长时间没有回答”不能单独判定为停滞，因为人可能正在思考、阅读或暂时离开。更可信的非生产性循环通常表现为多次尝试仍没有新证据、重复同类错误或策略、无法形成下一步，并伴随明显挫败或偏离目标。健康挣扎若仍在产生策略变化和局部成果，应允许继续。

超过阶段预算时不自动判定失败，而依次考虑：继续并明确缩减范围、改变提示或表示方式、拆小问题、转做不受阻部分、冻结扩展项、切换为最小交付，或尽早暴露无法可信完成的风险。学习插槽只有在真实期限受威胁、继续尝试的收益已低于交付风险且人明确同意时，才由 AI 局部接管。

普通学习、发散、复杂推理以及人已经感到焦虑的场景不使用可见倒计时。硬截止只来源于真实外部后果，不把内部预算伪装成不可突破的期限。

### 6.3 最小认知包

陌生主题不从“解释一切”开始。AI 应先提供：

1. 一张包含 3—5 个节点的最小图式；
2. 5—8 个马上会使用的术语及通俗定义；
3. 一条主要因果链；
4. 一个代表性正常例子；
5. 两个主要故障模式及可见症状。

最小认知包只包含支撑当前判断所需的知识。随着人的已有知识增加，脚手架应逐步撤除，避免新手解释对熟练者形成冗余负担。

### 6.4 低摩擦能力诊断

诊断证据按以下优先级收集：

1. 自然任务表现：问题描述、预测、取舍、查错和整合；
2. 微型验证：解释关键概念、预测一处变化、指出一个风险；
3. 定向练习：仅在证据冲突、用户主动学习或疑似缺少前置知识时使用。

诊断题可以设置对应真实误解的干扰项，但不能成为隐蔽陷阱：

- 明示要确认的概念和目的；
- 每题主要测一个概念；
- 错误选项对应可解释的常见误解；
- 允许“信息不足”和“我不确定”；
- 结合理由和信心判断，而不只看答案；
- 一次错误只算观察；
- 至少两个不同情境重复出现同类错误，并排除题意歧义后，才提示前置知识缺口。

AI 可以说“当前证据显示某项能力尚未稳定”，不能据此推断人的智力、人格、职业等级或心理状态。

### 6.5 自我效能三账

任务结束时分别判断：

| 账目 | 回答的问题 |
| --- | --- |
| 任务结果 | 共同产出的结果本身完成得怎样？ |
| 个人独立能力 | 撤除当前 AI 支架后，人能否解释、复现或迁移？ |
| 人机协作能力 | 人是否有效定义、理解、质疑、取舍、整合和验证共同产出？ |

同时记录 AI 支援程度：

- A0：无帮助；
- A1：提醒或检查清单；
- A2：局部提示；
- A3：共同推导或部分实现；
- A4：AI 主导完成。

A4 可以对应优秀的任务结果和较强的协作表现，但不能据此提升个人独立能力。求助本身也不扣分；缺乏独立证据时应标记“待验证”，而不是武断地判为能力低。

正反馈必须指向可观察贡献，例如正确的边界判断、反例、风险取舍或独立实现，不使用无证据的能力赞美。

### 6.6 能力矩阵与学习阶梯

研发专项能力按项目动态选择，例如语言与 API、平台、数据与事务、调试、验证、安全、架构和业务领域。

长期人机协作能力包括：

- 问题定义；
- 理解与建模；
- 错误和无依据假设检测；
- 权衡与可逆性判断；
- 真实系统整合；
- 澄清时机判断；
- 验证证据判断；
- 最终决策所有权；
- 表示选择与转换；
- 联想、类比校准和抽象迁移。

学习难度可按以下阶梯渐进：

```text
选择 → 填空 → 一行代码 → 局部代码块 → 完整函数 → 小型组件 → 独立设计与验证
```

阶梯不是固定课程，也不是永久能力标签。陌生领域从低级开始；连续出现低支援成功后逐步升级；受阻时缩小范围、增加骨架或降级；高压力时可以暂停学习插槽。

学习轨不得成为主线交付的强依赖：插槽应短小、可撤回、可由 AI 接管，并与当前任务直接相关。时间、压力或认知负担明显上升时，应优先保持业务主线，只把真正影响后续维护和判断的学习债务留待复盘处理。

每轮最多选择一个主要瓶颈、一个必要前置能力和一个通用协作能力。训练采用逐步撤除支援：

```text
AI 示范 → 给步骤 → 给局部提示 → 人独立完成 → 换情境验证迁移
```

有效反馈采用“结果—原因—下一步”，不以泛泛表扬或立即给出完整答案代替指导。

#### 能力证据快照与权威画像

长期方向是为人维护一份跨任务演进的权威能力画像，而不是让各项目分别形成互相冲突的永久标签。权威单例表示单一事实来源，不表示把人的能力压缩成单一等级；语言与 API、架构、业务、验证和人机协作等能力仍按领域、抽象层和情境分别判断。

每个任务只产生当时的能力证据快照，记录可观察表现、任务情境、AI 支援程度、时间、可信度和适用边界。一次成功或失败不能直接升级或降级权威画像；在复盘或定期汇总时，依据跨情境重复、迁移表现、证据新旧和冲突情况提出画像变更。旧画像与当前表现冲突时标记复核，不强迫现实服从已有标签。

任务状态只保存学习模式或证据文件引用，不保存完整能力判断。任务快照可以随任务放置，便于保留项目和抽象层语境；权威画像究竟放在跨产品可见的个人全局位置，还是采用全局权威加项目视图，留待价值验证和隐私、同步需求明确后决定。Codex Memory 等产品记忆只作为召回层，不能覆盖人的可审查权威画像。

### 6.7 自然对话、输出预算与理解修复

没有适用于所有人的固定最佳字数。输出负担取决于新概念数量、关系复杂度、信息密度、人的已有知识和当前压力，因此字数只能作为软预算。

AI 默认应：

- 先给核心结论和当前最有用的信息；
- 一轮只推进一个主要问题，默认只提出一个需要回答的问题；
- 控制每轮新增概念和关系，而不是一次预支全部背景；
- 重要风险、限制和不确定性保持可见，不藏入可选展开内容；
- 用户继续追问时展开，出现迟疑、疲劳或“不想填”时收缩；
- 在内部维护任务结构，让人可以用自然语言自由表达，不默认展示完整模板。

AI 提问前应判断：答案是否可能改变方案、风险、权限或验证方式；能否从现有上下文安全推断；错误假设的成本是否高于提问成本。只有问题具有足够信息价值时才应打断用户，否则应写明可纠正的暂定假设并继续推进。

引导默认按以下顺序逐步增加约束：

```text
自然开放问题 → 一个思考线索 → 一个代表性例子 → 少量候选方向 → 必要时才使用模板
```

初学者面对陌生问题时，可以提示其用自己的话重述“要改变什么、不能破坏什么”，但不强制每次复述，也不要求其先掌握工作流术语。发散阶段先收集想法，不同时要求排序；只有形成候选集合并说明影响、发生可能性、可发现性和恢复成本等判断依据后，才进入收敛。

模板只有在能够降低而不是增加摩擦时才显式展示，例如正式交接、高风险逐项确认、多对象比较，或用户主动要求。上一轮讨论中“3 个场景 × 5 个字段一次填写”被确认为失败示例：它形式上覆盖了信息，实际上增加了阅读和行动门槛。

当人表示“看不懂”时，AI 不能只用更多文字重复原解释，也不能立即把理解责任变成考试。建议采用以下微循环：

1. 承认当前表达没有建立共同理解；
2. 缩减为一句核心解释或一个具体例子，不引入额外术语；
3. 用一个低摩擦问题定位断点，例如术语、前提、因果关系或实际操作；
4. 根据回答只补一个必要前置概念或换一种表示；
5. 通过自然复述、预测或真实操作取得“足以继续”的理解证据，而不是要求完整答题。

理解是双方逐步建立的共同状态，不是 AI 输出文字后的自动结果。AI 无法保证人已经理解，只能通过后续判断和操作获得相称证据。

#### 隐含信息提取与风险分级确认

人的自然表达往往已经隐含目的、不变量、约束、偏好和风险判断。AI 应先提取并用简短重述反映理解，不要求人把这些内容重新填写成结构化表单。

确认强度由推断错误的影响、可逆性和不确定性决定：

- 低风险、容易恢复：AI 可以重述暂定理解后继续，人随时纠正；
- 中风险：AI 明示关键假设和影响，给人一个自然的纠正机会；
- 高影响、难恢复或不可逆：不能把沉默当作同意，必须取得主动确认；
- 应急任务：允许先交付后学习，但安全底线、重要假设、验证债务和事后复盘不能消失。

重述的目的不是要求人逐项签字，而是建立共同理解。例如：“我暂按向业务层开放 Batch、同时保持既有 endpoint 和 ChangeSet 行为推进；如果你的重点不同请直接纠正。”

#### 建设性对抗与认知摩擦

人机协作不是一方无条件顺从另一方。AI 发现重大矛盾、无依据假设、风险盲点或方案越界时，应提出异议；人也应能够质疑 AI 的事实、推理和取舍。

有生产力的认知摩擦应具有以下特征：

- 指向具体事实、矛盾或证据缺口；
- 解释风险的因果链和可能后果；
- 与影响和可逆性相称；
- 提供低成本验证、替代方案或恢复路径；
- 把最终价值判断和风险接受留给有责任的人。

无生产力的摩擦包括机械引用流程、泛泛宣称风险、对低价值细节反复确认、用专业术语压服用户，以及只阻止而不帮助推进。

风险沟通可以遵循“观察—原因—后果—验证或替代—决策归属”的逻辑，但不要求每次显式套用固定话术。目标不是让所有交互都没有不适，而是消除仪式性负担，保留能够改善理解和决策的必要挑战。

#### 状态冲突的低摩擦处理

任务文档、后续对话、代码事实和 AI 摘要可能出现不一致。时间更晚不必然代表优先级更高，初始定义也不是不可修改的永久结论。发现疑似冲突时，AI 应：

1. 先判断是否只是补充关系、不同抽象层描述或术语差异；
2. 只暂停受影响的动作，不阻塞整个任务；
3. 简短呈现新旧说法、来源和可能影响；
4. 依据安全与合规不变量、人明确确认的变更、已批准文档、暂定假设、AI 推断的顺序判断；
5. 只有仍然互斥且会改变方向时，才请求人裁决；
6. 裁决后更新权威状态，将旧决定标记为已取代并保留来源，而不是静默覆盖。

AI 应承担检索、比对、真假冲突判断和影响分析，不能把原始差异全部倾倒给人。冲突警示需要说明为什么它可能重要，并给出最小必要选择；低价值措辞差异和能够安全合并的补充信息不应制造新的确认流程。

### 6.8 表示形式路由与多模态

| 信息结构 | 优先形式 |
| --- | --- |
| 单一结论与原因 | 短文字 |
| 并列项和检查项 | 列表 |
| 多对象重复字段比较 | 表格 |
| 层级、依赖和组件关系 | 结构图或树 |
| 分支、因果和数据流 | 流程图 |
| 状态变化和异步过程 | 时间线或状态图 |
| 精确执行语义 | 代码 |
| 抽象规则落地 | 代表性例子 |
| 参数变化影响结果 | 交互演示 |
| 连续运动和界面操作 | 动画或短视频 |

采用“一份语义、多个互补视图”：文字负责结论和解释，表格负责精确比较，图负责关系，示例负责落地，代码负责执行语义。每个新增视图必须回答前一视图没有回答的问题，避免机械重复。

信息按需展开：

- L0：一句结论、当前状态和下一步；
- L1：核心依据或小型结构化视图；
- L2：完整边界、日志、代码和证据。

视频和动画是后置选择；使用时应提供用户控制、静态摘要、字幕或文字稿及关键帧。图示应有文字说明，颜色不能成为唯一编码，重要信息必须可搜索、可复制并具有静态回退。

#### 叙事与微型故事

故事适合承载情境、行动、因果、后果和部分难以直接规则化的经验。当抽象术语或规则难以形成心智模型时，AI 可以使用贴近人已有经验的短故事，帮助其看见“谁在什么条件下做了什么，为什么会产生这个结果”。

故事的使用应保持克制：

- 优先使用能直接支撑当前判断的微型故事，不为生动而增加无关情节；
- 明确故事要解释的关键因果，不让偶然细节冒充一般规律；
- 说明它只是例子、反例或假设场景，而不是统计证据；
- 必要时指出适用边界或提供一个相反案例；
- 最后回收到正式概念、规则、接口或验证要求。

推荐逻辑是“短故事建立情境 → 点出关键因果 → 声明边界 → 回到正式模型”。它是按需选择的表达工具，不是每次解释都必须执行的固定格式。

故事可以帮助理解和记忆，但叙事连贯性也可能掩盖证据缺口、夸大因果或通过情绪感染促成未经审查的接受。高风险决策仍应展示精确契约、限制、数据和验证证据，不能以“这个故事很有说服力”代替事实成立。

### 6.9 可见进度

进度反馈展示真实工作状态和可验证成果：

- 已完成的能力或产物；
- 当前活动；
- 尚未确认的假设和风险；
- 剩余步骤及依赖；
- 用户下一次需要介入的节点；
- 新发现导致的范围变化。

不使用虚假百分比、XP、连续签到、排行榜、随机奖励、倒计时或损失厌恶机制。目标是建立胜任感和控制感，而不是延长使用时间或制造成瘾。

### 6.10 联想、类比与抽象回收

联想分为两个阶段：

1. 发散：从熟悉经验产生多个候选联系，暂不要求全部严谨；
2. 收敛：比较关系结构、约束和变化过程，淘汰只有表面相似的联系。

重要类比应说明：

- 要解释的目标概念；
- 熟悉来源；
- 对象、关系和约束的映射；
- 可以推出什么；
- 不能推出什么；
- 最可能误导之处和反例；
- 离开类比后的正式定义；
- 换一个情境后的迁移结果。

类比用于建立心智模型，不能代替规范、代码、测试或真实系统证据。必要时比较两个不同类比，以帮助抽取共同结构而不是记住故事。

#### 先例与成熟模式

面对陌生、高不确定或已有成熟实践的主题，AI 应在人的初始问题模型形成后，按需提供一个具体先例作为认知锚点。先例不仅用于复用实现，也用于提供词汇、典型边界、因果结构、故障模式和可比较的设计选择，使人的答案从“消费一个结论”转为“比较已有实例与当前任务”。

先例分析应区分四种结果：

- 可直接采用的成熟结构；
- 需要结合当前约束改造的机制；
- 适合作为反例或风险提示的做法；
- 现有方案没有覆盖、需要自行设计和验证的部分。

优先比较问题结构和适用条件，而不是复制目录、角色、术语或模板。必要时提供两个具有差异的实例，降低单一先例造成的锚定、设计固着和权威偏见。研究深度仍由任务风险、未知程度和预期复用收益决定；低风险或已有充分证据的任务不强制进行社区扫描。

### 6.11 文档路由

文档量由复用价值、决策成本、风险、寿命和受众决定，不由代码行数决定。

| 未来需要回答的问题 | 文档载体 |
| --- | --- |
| 单次任务发生了什么 | 工作包或交付记录 |
| 为什么这样选择 | 决策记录或设计文档 |
| 如何使用稳定能力 | 使用说明或 API 契约 |
| 出问题时如何处置 | Runbook |
| 某段代码为何反常 | 就地中文注释 |
| 可复用的协作模式 | 团队规范或知识库 |
| 尚未验证的想法 | 实验记录或待办 |

简单任务可以合并任务与实施记录；复杂任务可以拆分探索、证据、任务、实施、决策和审查文档。只记录影响决策的事实、容易遗忘的不变量和代码无法表达的取舍，不保存无复用价值的流水账。

文档必须能被检索、链接和再次使用。写了但无法发现、没有失效条件或长期无人维护，不构成知识沉淀。

#### 文档受众与审查面

完整任务文档、实施文档和证据记录主要承担 AI 连续执行、上下文恢复与独立审查，不默认要求人逐字通读。让人对无法现实审完的长文作整体批准，只会形成“审批已经发生”的假象，并把认知卸载重新变成阅读负担。

人应在与其责任匹配的抽象层审查承重信息：目的、业务不变量、改变方向的取舍、重大风险、待裁决事项和下一步。AI 从自然讨论和权威文档中生成一个最小审查面，默认只报告本轮变化并链接到正文；人根据风险、学习目标和疑点继续下钻。该视图不是第二份事实源，不能独立演化或静默覆盖完整文档。

完整文档仍必须人可追溯、可抽查。为降低摘要遗漏或偏置：明确区分已确认、AI 推断和未知；给出对应章节或证据入口；高风险决定要求明确确认；独立审查者检查全文中的承重结论，而不是只审 AI 摘要。理解和负责不等于逐行阅读，但也不能把判断权委托给不可见的 AI 闭环。

### 6.12 风险、验证与回退

风险至少考虑：

- 影响范围和可逆性；
- 数据、安全、权限和合规；
- 并发、状态、幂等和外部依赖；
- 公共接口与生产行为；
- 人对该区域的熟悉程度；
- 当前证据缺口。

每个关键风险应对应消除、降低、验证、监控、回退或由有权人员接受。实现完成和验证完成必须分开表达。

验证不是测试数量竞赛。先说明一个证据能排除什么风险、不能排除什么，再按失效边界选择编译、静态审查、针对性单元测试、集成/功能验证、真实请求重放、人工验收或运行观测。没有授权或环境不合适时，输出精确的人工验证契约并保留验证债务；不得用静态推断冒充执行证据，也不得因测试全绿声称业务风险已经消失。

中途变化按影响回退：

- 目标、范围或不变量改变：回到任务理解；
- 方案因果错误或影响面扩大：回到实施讨论；
- 局部实现错误：留在代码实施；
- 旧审查证据依赖失效假设：明确作废并重新审查。

## 8. 常见反模式

- “人许愿，AI 实现”，人不参与问题定义、取舍和验证；
- AI 先给完整答案，人把熟悉感误认为独立掌握；
- 根据 Prompt 长短、响应速度或一次错误给人贴能力标签；
- 使用隐蔽陷阱、文字游戏或羞辱式纠错；
- 任务成功全部归因于人，或把使用 AI 本身视为能力不足；
- 用大量背景和专业术语掩盖目标仍不清楚；
- 在意图和行为未确定时过早深入代码或底层原理；
- 强制解释所有实现层级，制造无限认知递归；
- 强制隐藏所有底层细节，使抽象泄漏在生产故障时突然暴露；
- 为每个内容强配图、视频或多个重复视图；
- 输出覆盖所有相关信息的长文，却没有控制人每轮需要整合的概念和决定；
- 把工作流模板直接变成人必须逐项填写的问卷；
- 人说“看不懂”后继续追加长篇解释，或立即要求其完成理解测试；
- 要求人严格按单一抽象层表达，打断自然联想和跨层思考；
- 把人的沉默一律视为对高风险推断的确认；
- 为保持表面和谐而隐瞒重要异议，或反过来用泛化风险和术语制造权威感；
- 只告诉人“不能做”，却不解释后果、验证办法或可逆替代方案；
- 发现状态差异后沉默采用其中一项，或反过来把所有措辞差异都升级成人工审批；
- 用“最新内容覆盖一切”或“初始文档永不改变”代替来源、层次和影响判断；
- 用生动类比代替真实证据；
- 用生动故事制造确定感，却不说明它只是例子、适用边界或正式依据；
- 为了吸引注意加入与当前判断无关的情节和情绪刺激；
- 把 AI 自审称为独立审查；
- 代码实施后静默替人选择独立审查方式，并长时间跨阶段执行；
- 把几百行或几千行差异直接交给人，再把遗漏问题归因于人的直觉不足；
- 把编译通过、测试通过等同于需求正确和风险消失；
- 为展示严谨、提高覆盖率或修复每个缺陷而条件反射式增加测试；
- 只凭静态怀疑把 N+1 等性能问题判为必须重构，不测量实际业务影响；
- 由 AI 单方面写复盘总结、塞进架构文档并直接关单；
- 把架构文档写成逐轮调查、实现和验证流水账；
- 为展示学习而阻断紧急交付，或以紧急为由永久取消学习；
- 用单一总分、排行榜、连胜或虚假百分比衡量能力和进度；
- 每个任务都生成完整文档，形成无人检索的文档坟场；
- 应急结束后不偿还验证、审查和认知债务；
- 只依靠人的记忆、AI 会话上下文或一句提示词维持流程。

## 9. 科学表述边界

本文借鉴认知卸载、自动化偏差、认知负荷、脚手架、自我效能、检索练习、类比迁移、多媒体学习和复盘等研究，但不把工程化设计推论包装成已经普遍验证的定律。

应保持以下边界：

- 现有证据支持 AI 可能改变认知分工并诱发过度依赖风险，但不足以断言使用 AI 必然导致永久认知下降；
- 压力可能削弱部分执行功能，但其效果受任务、控制感、强度和个体差异影响，不是简单的单调关系；
- 独立预测有助于暴露当前模型，但一次预测正确不等于掌握；
- 能解释不等于能执行，执行一次不等于能够迁移；
- 自我效能不等于客观能力，必须结合任务和迁移证据校准；
- 选择、填空、一行代码到函数是合理的脚手架设计，不是唯一且普遍适用的固定序列；
- 刻意练习能改善特定能力，但不能单独解释综合表现，远迁移通常有限；
- 图文结合可能改善理解，动画和视频并不天然优于静态图或文字；
- 类比可以帮助理解，不能证明两个系统具有相同机制；
- 结构化复盘通常有益，但评分、徽章和排行榜可能诱发刷指标；
- 80/20 不是普遍成立的教育科学定律；
- 本工作流不是心理测评，不推断智力、人格、心理健康或职业等级；
- 本工作流应通过真实任务持续修订，而不是宣称对所有人和所有任务最优。

## 10. 下一阶段：执行保障机制

本版回答“理想的人机协作应该怎样进行”，尚未回答“怎样使这些行为在真实压力、长任务和跨会话情况下稳定发生”。

### 10.1 已确认的问题

- 人的工作记忆有限，依赖主观记忆维护流程不可靠；
- 文档可能无人阅读、内容过期、互相冲突或流于填表；
- AI 的上下文有限，额外维护流程状态会挤占任务上下文并可能降低工作质量；
- 会话压缩、模型切换和人员交接可能丢失关键状态；
- 提示语、约定和自觉属于软约束，无法稳定保证阶段顺序、退出条件和独立审查；
- 过强门禁又可能制造官僚负担、阻塞应急交付并诱发形式主义。

### 10.2 下一阶段目标

设计一套低摩擦、可观察、可中断、可恢复、按风险调节强度的执行保障机制。它至少需要回答：

1. 五个阶段及其退出条件如何被可靠触发和记录；
2. 如何让独立预测发生在答案暴露之前，同时不阻塞紧急任务；
3. 最小认知包、关键决策、验证债务和学习状态如何跨会话、模型和人员持续；
4. 独立审查怎样在上下文和证据方法上形成真实隔离；
5. 压力模式下哪些环节可以压缩，哪些安全边界不能绕过；
6. 未完成的验证、审查、文档和认知债务如何被自动发现；
7. 如何防止模板化填充、刷指标和形式主义；
8. 机制失效时如何降级、恢复并保留人工接管；
9. 如何收集足够证据评估机制，又不演变为人员监控或心理画像；
10. 如何控制保障机制自身的上下文、维护和使用成本。

### 10.3 本阶段明确不做

本次不预设必须采用：

- 插件或 IDE 扩展；
- Agent 技能、系统提示或单一模型；
- 工作流引擎；
- 数据库、状态服务器或知识图谱；
- PR 门禁或 CI 自动化；
- 聊天机器人或独立应用；
- 复杂评分系统。

下一阶段应先定义保障目标、威胁模型、失败模式和验收标准，再比较人工检查点、结构化状态、工具集成、自动门禁等不同实现手段。

### 10.4 首个试运行：Out.WebApi Batch 重构

`Interfaces/SunWard.Out.WebApi` 增加业务层 Batch 能力作为本工作流的首个真实试运行。以下是任务理解阶段形成的初始验收假设，仍需在实施讨论中校准：

- **业务结果**：既有业务 endpoint 的有效调用链不能因重构失效；新增批量能力能够支持目标业务场景。
- **开发体验**：常见批量 CRUD 调用简洁、容易发现和理解；业务开发者不需要接触 multipart、boundary、Content-ID 等协议细节。
- **结构质量**：公共组织语义与内部传输协议边界清楚；复用已有 Batch/ChangeSet 协议能力，不重复实现转换和发送链路。
- **可维护性**：代码长度和类型数量与真实复杂度相称；不引入无当前需求支撑的 ORM、Planner、Writer、工作流 DSL 或其他预扩展抽象。
- **协议正确性**：普通 Batch 与原子 ChangeSet 的语义、失败结果和事务边界符合 Dataverse Web API 的实际行为及官方约束。
- **工作流有效性**：流程应帮助人理解并审查上述取舍，同时不显著增加阅读、填表和交付阻力；若复杂度没有带来可观察收益，应缩减、重构或否定相应机制。

这里的“优雅”不是单一审美结论，而是对调用便利、表达简洁、边界清楚、复用充分、理解成本和维护成本的综合期待。实施讨论需要把相关部分转化为可观察证据，但不应为了可量化而制造机械指标。

试运行同时观察流程自身，而不预设固定字数、问题数量或时间比例：

- 从提出任务到首次有效行动的时间；
- AI 要求人作出决定的次数及其必要性；
- 人是否出现明显阅读、填表、反复解释或决策疲劳；
- 学习插槽是否阻塞业务主线；
- 流程是否实际减少方向性返工、无依据假设和审查遗漏；
- 人是否产生绕过流程的冲动，以及原因是什么。

这些信号用于发现趋势和修订机制，不用于人员绩效评分。若流程负担持续高于它减少的风险与产生的学习收益，应主动缩减，而不是要求协作者投入更多意志力维持它。

### 10.5 状态载体与上下文压缩观察

当前形成的轻量假设是：影响后续判断的重要状态需要持久化，临时推理和探索过程保留在对话上下文；只有阶段边界、重大决定、风险变化或交接需要时才更新持久化状态，不保存全部聊天流水。

当前所有权已明确为个人资产，不作为 SUNWARD CRM 团队规范。本文暂时借当前仓库完成设计和试运行，不代表最终必须存放在该仓库或由团队共同维护。

持久化位置尚未决定。候选方向至少包括：

- **仓库内**：天然贴近代码、分支、评审和团队上下文，但可能产生临时文档、仓库噪声、敏感信息和生命周期问题；
- **产品专用全局目录**：适合对应产品自动发现，却不天然对其他 AI 产品可见，可能产生迁移、同步和供应商锁定，因此不宜作为跨产品个人规范的唯一权威来源；
- **产品无关的个人全局位置**：适合个人偏好、通用规范和长期学习状态，但仍需解决不同产品的文件访问权限、路径差异、任务关联、发现和加载方式；
- **按所有权拆分的混合方式**：任务与团队事实随仓库保存，个人偏好、跨任务索引或学习状态保存在仓库之外，但需要解决引用、同步和冲突。

位置决策应依据状态由谁拥有、谁需要读取、是否随代码版本变化、隐私和审计要求、生命周期及跨产品可移植性，而不是仅凭某个产品当前默认行为。

当前长对话即将发生的自然上下文压缩作为一次观察点，不主动触发或操纵。压缩后观察 AI 是否：

- 仍能识别当前任务是设计人机协作工作流的执行保障机制，而不是直接实施 Batch；
- 保留“重要状态持久化、临时推理留在对话、位置尚未决定”的最新共识；
- 能从权威文档恢复稳定状态，而不要求人重复已经确认的全部背景；
- 不把候选假设误报为最终决定；
- 能从未决问题继续推进，同时诚实指出无法恢复的临时细节；
- 不因恢复上下文而输出一篇重复历史的长文。

这只是一次案例观察，不能单次证明机制有效；结果应进入复盘，用于改进最小认知包、状态更新时机和恢复流程。

2026-08-09 的首次自然压缩中，AI 保留了当前目标、权威文档位置、最近一次修改失败的状态和最新优先级修正，未要求人重复背景，也未把 Batch 误当成已进入代码实施。恢复仍依赖系统摘要并需要核对外部文档，因此这只是一个正向样本，不足以证明长期稳定性。

同日第二次自然压缩发生在首版实施设计阶段。恢复内容保留了两层 `AGENTS.md` 的实际位置、需要纠正的旧判断、当前文档受众问题和下一步修改方向。这进一步说明“最小持久状态加外部文档核对”具有恢复价值，但仍依赖系统生成摘要；连续两个正向样本不能替代后续对遗漏、冲突和错误恢复的检验。

### 10.6 优先级对齐与价值验证顺序

当前首先要验证的不是跨产品分发能力，而是本工作流能否在不显著拖慢业务交付的前提下：

- 提升人的独立解释、判断和迁移能力；
- 通过可观察贡献改善并校准自我效能，避免无力感或虚高；
- 降低不必要的阅读、理解、填表和决策负担；
- 减少方向性返工、无依据假设、过度抽象和审查遗漏；
- 保持自然、可接受的协作体验。

这些价值假设优先在主要使用的单一产品和真实 Batch 重构中验证。跨产品核心、适配器、同步或远程服务均作为后续候选；只有已有证据表明工作流值得保留，且迁移需求真实出现时，才投入设计。

人的当前重点与 AI 根据技术脉络推导出的“下一步”可能不同。协作中应区分“当前共同目标”“AI 建议的后续方向”和“已推迟事项”。人的最新明确优先级决定当前议程；AI 仍应指出具体风险，但不能以技术上的连续性替代共同决策。

优先级不需要每轮机械确认。只有出现明显分叉、范围扩张、时间预算变化、核心假设被替换或交付物改变时，AI 才用简短重述重新对齐；其余有价值但非当前必要的方向进入待办，不中断主线。

### 10.7 共同航标

长时间讨论中，人和 AI 都可能保留局部内容，却逐渐失去共同目标和下一步。使用可纠正的“共同航标”重新激活方向，而不是依靠双方持续记忆或反复总结全部历史。

默认最小形式为一行：`目标 → 当前阶段 → 下一步`。在确有需要时可补充“已确定、待核实、暂缓”，但同一时刻只突出一个下一步。AI 负责从自然对话中起草，人只在不准确时纠正；推断不得伪装成已确认决定。

航标按事件触发，而不按固定轮数机械弹出。适合触发的事件包括阶段转换、明显话题分叉、中断后恢复、上下文压缩、AI 对当前方向置信度下降，以及不可逆或高影响行动之前。日常推进只报告发生变化的部分，避免把航标扩张成会议纪要、待办仓库或第二套项目管理系统。

未完成主线中出现灵感或旁支时，AI 应判断它是在补充还是替换当前议程。补充内容只在对话中保存轻量返回点，处理完后主动恢复原主线；只有人的新表达真实改变目标、优先级或交付物时，才更新共同下一步。不能因近期内容更显著而静默遗忘未闭合事项，也不能要求人负责提醒“说完后回去”。

试运行进一步暴露：临时旁支会自然成长为独立任务。人机协作规范最初由 Batch 讨论引出，后来已经形成自己的文档、Skill 实施和连续下一步，却没有自己的任务状态；恢复时只有 Batch 状态可见，容易把试点样本误认为当前主线。改进重点不是继续增加跨 session 特判，而是在旁支形成独立目标、持久产物和连续行动后，于自然检查点把它晋升为独立任务。多个任务可以同时活动，当前任务仍由人的表达和对话中的共同下一步确定，状态只负责恢复各自的位置。

上下文责任是双向的：人通过自然表达和必要状态帮助 AI 理解当前任务，AI 在请求判断、恢复或切换任务时，也要向人提供支持当前行动所需的最小上下文。任务状态和完整文档主要承担 AI 的可恢复上下文；即时摘要、代表性例子、主要权衡和明确交接则承担人的可理解上下文。双方都不应被迫从不完整线索猜测对方正在做什么。

该机制的有效性不以“展示过摘要”为证据，而观察它是否在保持低打扰的同时，帮助双方更快、更准确地识别当前目标和下一步，并减少重复询问、错误假设与方向性返工。

### 10.8 首版保障栈与收益优先

当前候选保障栈采用互补分工，而不是在 `AGENTS.md` 与 Skill 之间二选一：

- `AGENTS.md` 只保留少数常驻底线和 Skill 启动条件。它是比按需 Skill 更稳定的指令约束，但仍属于模型可偏离的软约束，不冒充确定性门禁；
- Skill 承载分阶段工作方法、交互判断和资源路由，通过渐进披露按需读取规范、示例和学习材料；
- 复杂任务以任务文件夹为持久化单元；小型机器可读状态只保存协作控制、唯一下一步和权威文档引用，任务目标、不变量、设计与学习证据按需进入对应文档；
- 脚本只负责格式校验、冲突检测、状态渲染等确定性工作；
- Hook 只在压缩和恢复等生命周期节点调用脚本、校验并重新注入最小状态，不自动改写语义共识。

首版不追求机制齐全，优先实现收益高、容易观察、能够快速产生正反馈的部分：自然表达中的目标与不变量提取、共同航标、低负担的阶段回顾，以及人的关键判断和贡献留痕。只有真实试运行反复暴露某类状态遗漏或恢复失败，才增加相应脚本、Hook 或门禁。

### 10.9 社区参考与自行设计边界

首版不从零发明规则路由、Skill 渐进披露、文件化状态、阶段产物和上下文恢复，也不整套照搬任一社区框架。采用“先以本工作流目标建立判断标准，再抽取候选机制，最后在真实任务中逐项验证”的顺序。

现有方案主要优化 Agent 的软件交付可靠性；人的独立判断、自我效能、认知负载、自然表达和脚手架撤除仍是本工作流需要自行设计和验证的核心。详细候选、反例和取舍见 [人机协作保障机制参考研究](human-ai-collaboration-reference-study.md)。

当前探索已经覆盖首版需要的主要机制类别，达到阶段退出条件。后续只对实施或试运行中出现的具体未知定向研究，不用项目数量和方法论完整度推迟试运行。

这项原则适用于整个工作流，而非只用于保障系统选型。承重、陌生或高风险问题先进行轻量先例勘察：任务理解看领域定义和真实事故，实施讨论看仓库先例与官方架构，编码看既有惯例和官方 API，审查看成熟审查/验证方法，复盘看 AAR、debrief 与无责事后分析。每次明确“借鉴、适配、自研/舍弃”，并以当前不变量和证据裁剪；低风险熟悉任务不强制研究。

| D-039 | 首版按收益和可验证性排序 | 已采纳 | 先获得可感知正反馈，再根据真实失败渐进增加自动化与复杂度 |
| D-040 | 先研究社区机制再实施首版 | 已采纳 | 复用已经验证的结构模式，同时用既定目标筛除不适合的整套流程 |
| D-041 | 采用机制抽取而非框架照搬 | 已采纳 | 候选框架的目标、任务规模和流程成本与个人能力成长目标并不完全一致 |
| D-042 | 社区参考探索达到退出条件 | 已采纳 | 主要机制类别已覆盖，继续扩展项目清单的边际收益低于进入首版设计 |
| D-043 | 将先例作为按需认知脚手架 | 已采纳 | 具体实例能连接熟悉经验与未知抽象，并提供可比较的结构、边界和失败模式 |
| D-044 | 先例必须分类取舍而非整套照搬 | 已采纳 | 区分直接采用、适配、反例和自行设计，避免锚定、设计固着与流行度偏见 |
| D-045 | 完整任务与实施文档主要服务 AI 执行、恢复和独立审查 | 已采纳，待试运行 | 避免要求人通读长文造成工作记忆占用和形式化批准，同时保持内容可追溯、可抽查 |
| D-046 | 人默认审查承重信息及其增量视图 | 已采纳，待试运行 | 让人的判断集中于目的、不变量、关键取舍、风险和下一步，不创建第二份漂移的事实源 |
| D-047 | 采用任务能力证据快照与个人权威能力画像的两级结构 | 已采纳，实施待验证 | 保留真实任务语境，同时避免项目快照直接成为永久标签或多个项目各自维护人的能力真相 |
| D-048 | 权威能力画像的物理位置和同步方式暂不确定 | 待验证 | 项目内视图、个人全局权威及跨产品同步涉及可见性、隐私、生命周期和迁移成本，当前证据不足以选型 |
| D-049 | 插入话题采用对话内返回点并主动恢复主线 | 已采纳，待试运行 | 人的灵感不应被阻止，也不能因近期内容更显著而让未闭合事项静默消失 |
| D-050 | 复杂任务采用任务文件夹与小型控制状态分工 | 已采纳，迁移待阶段边界 | 防止状态文件吸收任务、实施和学习正文，同时为按需文档和后续确定性校验保留扩展点 |
| D-051 | 持久旁支晋升为独立任务 | 已采纳，来自试运行失效 | 当旁支已有独立目标、持久产物和连续下一步时，为其建立自己的恢复状态，避免只有试点任务可见而误判主线 |
| D-052 | 上下文由人机双方共同提供 | 已采纳，来自试运行反馈 | 状态和完整文档支持 AI 恢复，最小摘要、例子、权衡与交接支持人理解和判断 |
| D-053 | 成熟模式检查点贯穿五阶段并按风险触发 | 已采纳，来自试运行与研究 | 复用先例和研究降低从零设计成本，但不让检索成为每阶段仪式 |
| D-054 | 审查采用风险—证据匹配而非测试数量目标 | 已采纳，来自生产逃逸经验与研究 | 不同证据覆盖不同失效边界，测试全绿不能替代编译、集成和真实场景证据 |
| D-055 | 人类代码审查必须提供按风险切分的脚手架 | 已采纳，来自试运行反馈 | 人无法可靠通读大规模 AI 产出，最小上下文、例子和已知权衡能保留有效判断 |
| D-056 | 复盘是交互式 debrief，不是 AI 完成摘要 | 已采纳，来自试运行失效与研究 | 共同反思、客观材料和行动转化才构成学习闭环，单方面总结不能代表人的参与 |
| D-057 | 架构、证据、审查、复盘按语义分流 | 已采纳，来自试运行失效 | 防止架构文档膨胀成流水日记，并降低恢复与审查成本 |
| D-058 | 新任务按实际阶段轻量初始化，并在不可持久化时显式降级 | 已采纳，来自 Skill 生命周期审查 | 不让状态设施强迫任务重走阶段，也不在只读或未知环境中猜测存储位置、静默失去恢复能力 |
