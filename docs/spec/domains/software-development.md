# 软件开发协作专项

> 地位：**当前软件开发领域专项**。本文件把旧 Chapter 01/02 中依赖软件研发语境的角色、抽象层、五阶段与证据实践从通用层分离出来。
>
> 通用规范见 [`../norms.md`](../norms.md)；通用工作流模型见 [`../workflows.md`](../workflows.md)；能力评估见 [`../evaluation.md`](../evaluation.md)。

## 1. 角色与责任

旧规范把 `Owner / Explorer / Thinker / Builder / Reviewer / Verifier / 流程维护者` 并列为“角色”。当前概念模型进一步区分参与者、功能角色与权威，因此这里按软件开发语境重新解释：

### 1.1 人类负责人的权威

人类负责人负责明确目的、范围和成功标准，作出关键业务/架构取舍，接受风险，选择深入学习深度并最终验收。这主要是**权威与责任配置**，而不是要求所有任务存在名为 `Owner` 的固定功能角色。

选择较低的深入学习强度，不等于放弃当前业务、架构、风险或验收责任所需的有效判断基础。人不需要掌握 AI 实现的每个底层细节，但应能在其承担的抽象层理解相关后果、解释或质疑关键证据，并在超出自身边界时知道何时需要更强验证或合格专业判断。

### 1.2 常用功能角色

| 功能角色 | 主要责任 |
| --- | --- |
| Explorer | 收集代码、规范、环境和历史事实；区分事实、推断与未知；不代替有权负责人作架构决策 |
| Thinker | 建立心智模型；提出方案、因果关系、反例、权衡和风险；不以设计代替事实验证 |
| Builder | 按确认方向完成最小必要变更；暴露假设和偏差；保存相称的验证证据 |
| Reviewer | 从任务目的和原始证据重新建立预期，再审查方案、代码和验证；不直接继承实施者结论 |
| Verifier | 在高风险任务中通过不同方法验证关键断言，例如规范核对、运行证据或反例实验 |
| 流程维护者 | 维护模板、文档路由和试运行反馈；不代替任务负责人作业务或技术决策 |

同一参与者可以承担多个功能角色。`Reviewer` 或 `Verifier` 的角色名称本身不产生独立性；需要的证明力取决于相对于目标失效来源的实际隔离。

## 2. 软件开发抽象层

旧规范使用 L0–L4 作为软件研发中的实用抽象路由：

| 层级 | 核心问题 |
| --- | --- |
| L0 结果层 | 最终要得到什么，什么算完成？ |
| L1 行为层 | 输入、输出、规则、不变量和失败表现是什么？ |
| L2 边界层 | 模块、接口、数据、状态和依赖如何协作？ |
| L3 实现层 | 算法、控制流、代码结构和 API 如何实现？ |
| L4 原理层 | SDK、协议、数据库、运行时或硬件为什么这样工作？ |

默认深度是经验路由，不是通用规范：

- 任务理解：L0—L1，必要时到 L2；
- 实施讨论：L1—L2，影响取舍时到 L3；
- 代码实施：L2—L3；
- 故障定位：依据证据按需下潜到 L4；
- 独立审查：重新覆盖 L0—L3，高风险点按需到 L4；
- 复盘沉淀：回升到 L0—L2，记录真正影响维护的底层结论。

明显下潜后应把影响结论的底层事实重新连接到可操作的上层意义。理解不要求递归掌握所有下层机制；需要多深取决于人的当前责任、责任相关能力需求、风险和深入学习目标。底层实现可以继续委托给 AI，只要委托没有使人失去在其责任层判断后果、证据和边界的能力基础。

人的自然表达可以同时包含业务目标、行为规则、质量期待与实现偏好；AI 应优先保留原意，再在后台拆分层次和关系。

能力证据不等于抽象层，旧 M0–M5 已转化到 [`../evaluation.md`](../evaluation.md) 统一解释。

## 3. 软件开发五阶段闭环

这五阶段是当前软件开发专项的默认工作流，不是所有领域必须采用的通用骨架。简单任务可以压缩或合并阶段；新证据可以使流程返回前序关注点。责任相关能力成长可以在任一阶段发生，不因此新增固定“学习阶段”。

### 3.1 阶段一：任务理解

**目的**

确认为什么做、要改变什么、什么算完成、什么不能破坏，并建立足以继续讨论的最小心智模型。

**输入**

- 原始需求、问题现象或故障信息；
- 已知上下文、限制和已有证据；
- 人当前的理解、预测、疑问或担忧。

**主要活动**

- 区分目的、手段、事实、推断和未知；
- AI 在完整答案前保留未闭合空间；人自然表达预测、疑问或担忧时记录并用于后续比较，不把外显回答变成门禁；
- 建立范围内、范围外事项和业务不变量；
- 对陌生主题提供最小认知包，而不是从底层解释一切；
- 仅在需要调节解释、责任相关能力支援或深入学习深度时使用低摩擦诊断。

**最小产物**

- 任务目的和当前问题；
- 基础业务场景；
- 范围、非目标和关键不变量；
- 成功与失败的可观察标准；
- 已知未知项及风险初判；
- 已自然出现的人的预测、疑问或担忧；没有时将独立建构证据标为未知。

简单任务可以在对话中完成；中高风险任务可形成任务文档或工作包。

**退出条件**

- 目的、范围和不变量已有与风险相称的共同理解证据；高影响结论已取得主动确认；
- 成功与失败可观察；
- 尚未解决的歧义不会根本改变后续方案；
- 协调者明确哪些内容是事实，哪些仍是假设。

退出判断采用“足以安全推进”，而不是“所有问题已经回答”。剩余未知可以被显式记录，并在真正影响方案或风险时再展开；风险目录和模板不能被当作必须逐项完成的访谈清单。

### 3.2 阶段二：实施讨论

**目的**

确认怎样以正确、稳定且不过度的方式完成任务，使人能够控制方案粒度和关键取舍，而不是控制每一行代码。

**输入**

- 已确认的任务目的、范围和不变量；
- 相关代码事实、规范和历史约束；
- 已自然出现的人的预测、疑问或担忧，以及独立建构证据状态。

**主要活动**

- 建立现状与目标调用链或因果链；
- 说明首选方案、可行替代方案和拒绝理由；
- 明确领域模型、架构边界、接口、数据和错误语义；
- 按风险下潜到架构与实施层，提供人可调节的必要上下文；
- 识别事务、并发、幂等、性能、N+1、安全等与任务相关的技术概念；当一个成熟概念能够准确组织当前实践、具有较高迁移价值且点明成本很低时，可以做一次简短“命名—连接—边界”，不因此中断主线；
- 让风险与验证方式一一对应；
- 区分可纠正工作假设与整包待批准草案；后者不得单独充当阶段关门；
- 标出少数承重、值得人判断的可调点；低收益繁琐细节可交 AI 或作可纠正默认；
- 保持下潜入口开放，或由人显式选择快速通道；
- 只有当较高强度学习确有价值、并需要暂时把一个有限认知动作交给人时，才建立学习插槽并明确所有权；概念点名、短解释或普通共同判断不需要先创建插槽；
- 明确实施期间允许的命令和验证权限。

**产物**

- 实施文档或工作包中的实施章节；
- 关键因果、不变量和接口变化；
- 影响范围、实施步骤和验证计划；
- 明确不做事项；
- 已露面的承重可调点及其结论；
- 必要的学习插槽（若有）和独立审查策略。

**退出条件**

- 人能解释为什么该方案足以达成目标；
- 人能提出或理解主要反例与取舍；
- 高风险假设具有验证方法或被显式接受；
- 方案粒度已经足以实施，但没有提前设计无真实需求的扩展点；
- 方向可判断，承重可调点已露面或人明示不再谈细，且下潜入口未被关闸话术关闭，或已明确选择快速通道。

不得仅以“人对整包默认方案说了 yes”或“点头后开写”作为退出信号。

**反模式**

- “上面整套默认是否直接采用？”成为唯一主问题，随后“你点头后进入代码实施”；
- `next_action` 在仍处实施讨论时写成“确认后开始实现”；
- 用“充分即停止”为整包点头关闸辩护，却未露面承重可调点、也未保留下潜入口。

### 3.3 阶段三：代码实施

**目的**

按已确认方向完成最小必要变更，保持主线交付；在不妨碍交付时保留责任相关成长机会，并按需提供定向练习。

**输入**

- 已确认的实施方案；
- 不变量、风险和验证计划；
- 学习插槽及文件或符号所有权（若有）。

**主要活动**

- 以可解释、可检查、可回退的小批量变更推进；
- AI 标示重要假设、影响点和未验证项；
- 存在学习插槽时，人可以参与选择、填空、局部代码或完整函数；插槽只代表较高强度的有限认知动作，不是所有学习机会的前提；
- 插槽交给人后，AI 不修改相同文件或符号，直到明确交还；
- 实现过程中若出现可迁移且与人的持续责任相关的成熟模式、失败机制或验证原则，可采用低成本概念连接；需要长时间展开时再按目的与压力决定是否继续；
- 发现需求或设计错误时返回任务理解或实施讨论；
- 记录实际实现相对实施文档的偏差及原因。

**产物**

- 最小范围的代码或配置变更；
- 变更说明和方案偏差；
- 已取得的静态或运行证据；
- 未验证事项、剩余风险和后续债务。

**退出条件**

- 请求范围已实现，没有静默扩大；
- 关键不变量未被破坏；
- 计划内且已获授权的验证已经完成；
- 未运行的编译、测试或环境验证被诚实标记为未执行；
- 人能在其承担的抽象层解释关键行为和失败模式。

### 3.4 阶段四：独立审查

**目的**

从实施过程之外重新验证任务、设计、代码和证据，降低实施者自审的同源偏差。

**输入**

- 原始任务文档；
- 实施文档；
- 最终差异；
- 验证证据和剩余风险。

**主要活动**

1. 实施结束先区分 Builder 自检与独立审查，向人说明 Reviewer/隔离方式；协作方式会改变时由人选择，不静默跨阶段长时间执行；
2. Reviewer 先读任务目的，独立写出预期行为、风险和反例；
3. 再读实施方案和最终差异，判断方向是否足以达成目的；
4. 按“变化—失效模式—业务后果—证据缺口”选择最有判别力的证据；
5. Builder 的解释只用于澄清，不能作为正确性证据；
6. 高风险任务增加不同方法的第二条验证链；
7. 人参与审查时，AI 按职责或风险拆分代码，提供目的、变化路径、代表性切片、已知权衡和具体判断，不要求人直接读完大差异；目标是建立足以支撑其责任的判断基础，而不是以阅读量证明参与。

审查至少覆盖目标正确性、设计一致性、代码质量与验证充分性。性能、N+1、并发、安全、兼容性和可观测性按变化路径与业务影响选择；没有代表性测量或实际业务收益时，不因静态怀疑顺手优化。

**产物**

- 阻断项、建议项和残余风险；
- 修复后的复审结论；
- 高风险断言的交叉验证证据。

**退出条件**

- 阻断项已关闭，或由有权负责人显式接受；
- 高风险交叉验证已完成；
- 人接受残余风险；
- 未执行的验证没有被表述为已通过。

### 3.5 阶段五：复盘沉淀

**目的**

人和 AI 基于真实经历，共同检验并修正对“结果为何发生”的理解，使下一次在同类情境中能判断和行动得更好。事实回顾、行动项和文档只是服务这一模型修正的手段，不是复盘价值本身。

**输入**

- 任务、方案、代码、验证和审查结果；
- 已自然出现的初始预测（若有）、独立建构证据状态与实际证据；
- 实施中的成功、偏差、摩擦和意外发现；
- 前序阶段明确留待复盘的预约、未结问题和人的已有反馈。

**主要活动**

- 先恢复明确的复盘预约和未结问题；预约是延迟分析承诺，不因“不改本单”而丢弃；
- 事实有分歧或需要恢复时才简述原本预期和实际发生；事实清楚时直接聚焦值得解释的成功、偏差、摩擦或判断变化；
- AI 参与过任务时公开自身观察；中途接手或仅主持时基于任务证据提出并标明推断；
- 需要补充时用真实场景、后果比较或反例形成理解桥梁，不以流畅说明或人的点头冒充共同理解；
- 共同检验当时为何这样判断、哪些条件促成结果、替代解释是否成立、什么能迁移；
- 按价值深入而非逐项等量盘问；相关预约可合并分析，未结队列不能静默消失；
- 按人的持续责任结算本次自然出现的能力证据、支援程度与未知；有更深入学习目标时，再结算专项练习、独立能力与迁移假设，不为形式评价强行安排测验；
- 分析后再路由：形成模型修正、确认无需行动、转研究、路由为债务/风险/能力证据，或由人明确跳过；真正承诺执行的重点行动才保持极少数。

**产物**

- 必要的结算/复盘记录；
- 决策记录、开发文档或运行手册的必要更新；
- 技术债务、认知债务和流程债务；
- 下一次协作的推荐起点。

**退出条件**

- 结果、证据、偏差和剩余风险已经结算；
- 每项明确预约均已有理由地处置；
- 对关键结果的理解已有共同检验后的修正、确认或待验证假设；没有行动价值时允许“无需改进”；
- 人已经参与复盘或明确选择跳过；
- 长期有效的信息已进入正确载体；
- 无价值的过程材料没有被误当作永久知识。

## 4. 阶段关注点分流

各阶段默认关注不同问题，避免把后一阶段议题提前倾倒，或在后一阶段无新证据地重开前一阶段共识。深度仍按风险调节。

| 关切类型 | 主阶段 | 说明 |
| --- | --- | --- |
| 目的、范围、业务不变量、成功/失败可观察 | 任务理解 | 先钉“做什么、什么不能坏” |
| 方案方向、落点与分层、写入/错误语义、命名与复用、关键架构取舍 | 实施讨论 | “打算怎么做”；按风险下潜，不要求每次完整设计说明书 |
| 把已确认方案变成代码，记录偏差与未验证项 | 代码实施 | 不重新竞选架构，除非方案无法兑现或不变量被破坏 |
| 业务正确性、不变量是否兑现、失效模式与证据、不可接受风险 | 独立审查 | 已钉死的优雅性/DRY/美感不默认重开，除非出现新的业务或安全证据 |
| 协作与流程薄弱点、可迁移教训、技术/认知/流程债务的下次路由 | 复盘 | 不为“补审美”改本单已接受实现；把债务路由到正确载体 |

审查中出现未讨论过的架构/优雅性问题时，应明确选择：返回实施讨论；本单接受并记录风险/债务；或路由到后续，而不是静默推翻已确认方向。

## 5. 与通用工作流的关系

软件五阶段是 [`../workflows.md`](../workflows.md) 中通用关注点的一种具体实现：

```text
任务理解        → frame
实施讨论        → deliberate / plan
代码实施        → act / produce
独立审查        → assure / evaluate
复盘沉淀        → reflect / learn
```

这张映射用于说明来源与专项化关系，不要求其他领域复制相同阶段名、退出条件、角色或技术证据。
