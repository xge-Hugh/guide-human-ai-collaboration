# 工作流模型

> 地位：**当前规格中的工作流模型**。本文件描述可复用的任务关注点与依赖关系，不规定所有人机协作必须采用固定阶段数或统一名称。

## 1. 工作流不是通用规范的同义词

通用规范定义协作必须保护的权威、证据和交互边界；工作流用于把这些要求组织进某类任务的推进顺序。

因此：

> norm ≠ workflow

一个领域可以采用不同阶段、循环或并行结构，只要不覆盖通用规范。

## 2. 可复用的有序关注点

从现有软件研发五阶段中可以抽取出一组更一般的关注点：

```text
frame the task
    ↓
deliberate / plan
    ↓
act / produce
    ↓
assure / evaluate
    ↓
reflect / learn
```

这里重要的是**依赖与职责**，不是固定五个阶段。

### 2.1 问题框定（frame）

建立当前目的、范围、成功/失败可观察条件、关键约束、不变量、未知与风险，使后续行动不会建立在根本不同的问题理解上。

### 2.2 思考与计划（deliberate / plan）

建立足以行动的因果模型、方案、取舍、假设、风险与验证思路，并让真正会改变方向的承重点获得相称的人类判断。

### 2.3 行动与产出（act / produce）

根据当前已建立的方向形成可观察结果；记录重要偏差、假设与未验证事项。实现形式由领域决定，可以是代码、实验、分析、文稿、决策、操作或其他产出。

### 2.4 保障与评估（assure / evaluate）

使用与目标断言和失效模式匹配的证据检查结果、过程或关键假设；在需要时引入实质独立的复核或不同证据链。

### 2.5 反思与学习（reflect / learn）

基于真实结果与反馈修正对“为什么发生”的理解，识别可迁移经验、失效机制、债务、研究问题或无需行动的结论。

## 3. 顺序是约束关系，不是一次性流水线

这些关注点可以：

- 合并：简单任务可能在一轮对话中完成框定、计划和行动；
- 重复：新证据可能要求回到问题框定或重新计划；
- 并行：研究、验证或学习活动可以跨越多个执行步骤；
- 省略显式阶段：低风险机械任务不需要把每个关注点做成可见流程。

只有当某个关注点的缺失会实质改变判断、风险或后续责任时，才需要显式展开。

关注点可以交融，不表示相邻转换具有相同强度。框定与计划主要修正共同理解，可以频繁往返；从计划进入行动则开始改变真实产物、外部状态或后续责任，通常需要更强的依赖闭合、权限与可观察转换。就绪应按拟行动内容的依赖局部判断：一项承重决定未闭合时，不启动依赖它的行动，但不阻塞与它无关且安全可逆的调查、讨论或准备工作。

## 4. 阶段退出不能靠形式信号替代语义条件

“阶段已经讨论过”“人说了 yes”“有一份文档”“测试全绿”都不能单独证明对应关注点已经满足。

退出/推进条件应与该关注点的目的相匹配，例如：

- 框定是否有足以继续的共同理解与风险边界；
- 计划是否暴露了承重假设和验证方法；
- 行动是否诚实记录偏差和未验证项；
- 保障证据是否覆盖目标失效模式；
- 反思是否产生或检验了对结果成因的模型，而不是只完成总结仪式。

## 5. 工作流专项化

领域专项可以增加：

- 更具体的阶段名与产物；
- 领域角色和权限；
- 专门的证据类型；
- 技术失败模式；
- 更强的审查或恢复要求；
- 领域特有的术语与抽象层。

专项化关系是：

```text
general norms
    constrain
workflow archetype
    specialized by
specific domain workflow
```

专项不得反向覆盖通用权威与认识论约束。

当前软件开发专项见 [`domains/software-development.md`](domains/software-development.md)。

## 6. 工作流是否足够的判断

工作流不是越完整越好。只有新的关注点回答了现有阶段/关系无法表达的不同任务问题，或者已有关注点在某领域需要独立维护的更强规则时，才值得增加阶段或专项。

如果一个任务可以在更少显式步骤下保持相同的判断质量、证据、可恢复性与责任边界，就没有必要为了“走完流程”制造步骤。
