# 知情参与者救回的成功不能替代执行保障

- **日期**：2026-08-15
- **状态**：`candidate / evidence synthesis`（不升格为正式规范，不预设保障技术）
- **适用范围**：Cursor 平台、当前协作 Skill、IF-073 单次多阶段任务及其后续复盘
- **证据边界**：IF-073 的 task / state / review / retrospective 由人完整粘贴到本次复盘对话；临时 transcript 按人的要求不作为项目文件保留

## 主张（一句话）

知情参与者通过持续纠偏救回的任务成功，只能同时证明规范具有诊断价值、人的判断确实改变了结果，以及当前运行保障仍不足；它不能被算成 Skill 自主有效，也不能用 Skill 包结构健康来回答运行时是否可靠执行。

## 人的作用必须分成两类

### 不可替代的领域判断

本次人的参与真实改变了任务：

- 定义 mapping、JSON 示例和顾问口径的权威层级；
- 亲眼核对 CRM 字段与数据，协调顾问更正 WERKS、VKORG、ZZCPER；
- 回到设计书否决把 ZJHLX 示例值误当封闭域的审查建议；
- 选择风险、学习方式和是否追加审查。

这些属于业务语义、原始证据解释、风险接受和最终裁决。一个好的保障系统也不应替人做掉这些判断。

### 补偿 AI 与载体缺口的劳动

人还反复承担了另一类工作：

- 提醒 AI 不得静默裁掉证据冲突，并要求给出可亲眼核对的方法；
- 提醒实施讨论继续下潜到文件、入口、方法形态和承重点；
- 纠正把“强化”退化成重复讲解，以及生产代码残留教学脚手架；
- 发现任务文档混入新旧事实、完成态仍保留活动行动者/下一步、验证债务遗漏；
- 用原始设计书纠正经 AI 摘要后被污染的 Reviewer 输入；
- 在本项目复盘中指出：Skill 设计审查不能替代协作运行效果审查。

这些是流程推进、状态维护、规则召回和证据一致性工作。把它们统称为“人参与充分”，会掩盖人的疲劳并系统性高估 Skill。

因此后续评价至少要问：

> 人的投入中，哪些用于不可替代的领域判断，哪些用于补偿 AI 或保障设施本应承担的一致性维护？

当前不设固定比例或评分。

## 这次试点实际支持什么

### 支持度较强

1. **规范有诊断和修复价值**：试点暴露的大部分摩擦能被现有原则命名；人指出后，AI 多数能理解并调整。
2. **Skill 不是执行保障**：关键行为多次在首次机会没有发生，依靠人的提醒才恢复。
3. **最终正确不等于过程自主通过**：应区分 `pass`、经人提醒后 `recovered`、`fail` 与 `not_observed`，不能只看最终产物。
4. **知情用户会遮蔽新手风险**：本次人的项目知识和规范知识构成了额外保障。由此可以推断新用户缺少同等纠偏能力时风险更高，但尚无新用户实测，不能量化。

### 仍然未知

- 没有无 Skill 对照任务，不能估计 Skill 的净收益；
- 没有时间、返工量或注意力数据，不能判断总摩擦是否下降；
- 没有新用户试点，不能直接断言新用户会在哪些点失败；
- 没有跨任务表现，不能声称人的能力已经迁移；
- 本次学习机会主要由人主动开启，不能验证伴随式导师的主动调度；
- 没有编译、CI 和 SAP 联调证据，不能把协作收口等同于运行验证完成；
- 还不能分辨多少失效来自 Skill 文本、Cursor 平台、具体模型、长上下文或任务文档结构。

## 本次评价自身的错误

此前使用 Skill 设计审查框架得到“包结构健康、无需大改”，若只回答 frontmatter、渐进披露、引用路由和 eval 结构是否合理，这个结论可以成立；但把它外推为“当前人机协作 Skill 没有根本问题、无需重视保障”，就是类别错误。

需要分开的对象至少有：

| 层 | 回答的问题 |
| --- | --- |
| 规范 | 理想协作应满足什么，是否自洽、有价值 |
| Skill 载体 | 指令是否清楚、精简、可路由、可维护 |
| 运行表现 | 模型在真实任务中是否首次就执行关键规则 |
| 执行保障 | 状态、证据、阶段、不变量和债务能否被检查与恢复 |
| 结果与体验 | 任务是否成功，以及人的补偿成本、疲劳和学习收益 |

同一套 Skill 参与生成、整理并评价自身证据时，还会放大自证风险。直接失误是模型在本次推理中选错了评价对象；可复发根因则是项目尚未建立上述分层评价和独立证据链。这既是一次人机协作失误，也是当前保障缺口的实例，不应只记成“下次更谨慎”。

## 对项目方向的候选影响

IF-073 为“执行保障应成为下一条重点主线”提供了中强证据：现有规范已经足以发现许多问题，主要瓶颈转向关键规则能否在运行时被稳定召回、检查和留下可信状态。

但本轮只确认问题与优先级候选，不启动设计，也不预设插件、状态机、钩子、外部评测器或其他技术。后续若另立任务，应先定义：

1. 要保障的对象与不可机械化的人的判断边界；
2. 已观察到的失效模型及严重度；
3. 最小验收：关键行为从 `recovered` 转为 `pass`，同时人的补偿性劳动下降；
4. 保障本身的成本上限，避免把轻量协作变成流程门禁。

只有新的异质任务显示补偿性劳动下降、关键行为稳定前移，才支持把具体机制升格为稳定能力。
