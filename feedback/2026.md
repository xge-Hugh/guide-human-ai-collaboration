## 2026-08-28

### side chat ≠ second chat：辅助分支在主线程回归时发生 rejoin collision

- **场景**：进一步澄清真实使用：second separate chat 是另开完整会话，实际较少使用，尤其在高认知项目中会主动避免并行；side chat 则是附着于主线程/当前材料的辅助交互。等待期间有时会打开 side chat，但主线程可能在 side prompt 尚未发出或 side response 尚未闭合时先返回
- **发现**：不能再把 side chat 的成本简单解释为“第二任务切换”。更具体的候选失效是 `rejoin collision`：辅助分支尚未闭合，主线程重新变得可行动，人同时承担主线恢复、旁支收束与跨线程 reconciliation。side chat 本来用于解释/理解，却可能把认知成本从内容理解转成 interaction management
- **设计线索**：候选方向从“优化 side chat”进一步收窄为 `support without branch ownership`：理解修复、memory chunking、上下文压缩和局部解释尽量原位、低交互、可忽略，不要求人先写高信息密度 prompt，也不自动生成第二条必须管理的线程。可候选为 selection-aware micro commands、inline chunk anchors、ephemeral scratchpad、one-line reconstruction cue、progressive explanation；当前都不是产品需求
- **价值边界**：当前 human–AI 高价值环节越来越可能位于实施前的讨论、理解、证据解释与判断；减少人工执行量不等于减少认知成本。working memory / attention / cognitive control 是承重资源，但不把所有摩擦粗暴归因于单一 PFC “资源池”
- **状态**：`insight refinement` → [AI 等待期与时间协调候选](../docs/research/temporal-coordination/model.md)；新增 side chat / second chat 区分、rejoin collision 与 cognitive sidecar 候选；不改 live Skill / spec
- **后续**：自然观察 side chat 在何时降低理解成本、何时发生 rejoin collision；若要 prototype，优先低隐私、低主动性的原位支援，而不是生理/全行为状态推断


### 等待期细化观察：通知存在仍会轮询，thinking / 纸笔 / streaming / side chat 都是话轮内行为

- **场景**：进一步回顾真实使用：等待无输出时会刷手机、社交媒体、回消息；有可见 thinking 时会观察 AI 推理是否符合预期；有时用纸笔整理或留未来线索，虽觉得慢且字迹凌乱会产生不协调感，但写得稳定整洁时主观更平静；side chat 较少用于填等待，更多用于主线程内容理解不足时的解释/追问。现代 agent 工具已有完成弹窗/声音，但人仍会主动检查进展
- **发现**：先前把 polling 主要解释成缺少 completion notification 过强。更像是下一步被 AI 返回阻塞后，人面对“继续等待还是切走”的注意分配冲突；通知解决完成检测，不必然解决等待期间的悬置认知承诺。该观察还暴露更大的 turn-level abstraction gap：真实协作包含意图形成、输入修改、等待、thinking 监看、流式阅读、记录、side branch、整合与恢复，而不只是 human turn / AI turn
- **状态**：`insight refinement` → [AI 等待期与时间协调候选](../docs/research/temporal-coordination/model.md)；修正 `human-as-polling-loop` 为更窄的 `blocked-progression polling`，新增 interaction microstates 候选；仍不升级为 spec / live Skill
- **后续**：side chat 重点区分 latency-filling 与 comprehension branch，并观察它是否改善解释/预测/错误检测，还是增加跨线程 reconciliation；手机行为先按 boredom / habit / low-friction attention shift 研究，不用“dopamine”作单因果解释；纸笔的平静感先保留为 externalization / pace / attentional-boundary competing explanations

### AI 长响应等待暴露时间协调盲点：人被卡在半等待、半监控、半切换状态

- **场景**：日常人机协作中，AI 响应时间有时明显变长。等待期间，人会刷手机、切到其他实质任务、开 side chat，或反复检查 AI 是否完成；结果出现疲劳、难以跟上返回输出、上下文恢复成本和“是否已经完成”的持续监控焦虑
- **发现**：现有规范虽然在轻量性中顺带提到 waiting cost，也强调 working memory、attention、reconstruction 与 cognitive allocation，但尚未把“AI 暂时不可交互时人的认知状态”作为独立协作现象描述。候选问题不是怎样最大化等待期人类利用率，而是怎样降低 task suspension、completion monitoring 与 resumption/reconstruction 的总成本；尤其警惕系统把 completion detection 隐式转嫁给人，形成 `human-as-polling-loop`
- **状态**：`insight` → [AI 等待期与时间协调候选](../docs/research/temporal-coordination/model.md)；不直接修改 live Skill / spec，不开固定“等待阶段”
- **后续**：真实生态中自然观察等待期间的窗口/手机切换、轮询、side chat、返回后重建与疲劳；外部研究先用于校准 interruption/resumption、prospective-memory offloading 与 Human–LLM latency 的机制边界。若后续出现 decision-relevant competing explanations，再选择最小 field / runner / HCI evidence 方法

## 2026-08-17

### IF-038 旧版 Skill 试点：讨论交融被误读为可编码，预约完成被误读为复盘完成

- **场景**：在 Cursor 使用 2026-08-13 旧版协作 Skill 完成 IF-038 销售需求接口讨论、实现、审查与复盘。人说明任务理解与实施讨论无需形式化分关，AI 一度据此提议开始编码；后续大量顾问确认才钉住入参、覆盖、周月配对和时间窗口。复盘中三个预约处理完后，AI 又准备收口，但整体复盘尚未完成
- **发现**：阶段可以交融不等于其下游依赖已满足。讨论阶段之间主要改变认知状态，进入代码实施则会把尚未确认的语义固化到真实产物，需要更强的依赖闭合与可观察转换；同理，预约队列清空只是复盘退出条件之一，不能代替整体模型修正。两处均经人提醒恢复，应记为 `recovered`，不是首次 `pass`
- **人的作用与学习证据**：人既作出领域判断（SAP/CRM 粒度、配对键、错误语义、周数规则），也承担补偿性劳动（阻止过早编码、纠正文档路由与复盘退出）。复盘评价人和 AI 时不能使用对称清单：人的证据要结合判断、抽象层、支援和成长目标；AI 的证据要看边界保护、支援校准与首次机会可靠性；共同结果和补偿劳动另行结算
- **状态**：`evidence` → Issue #5（讨论过早闭合）、#6（复盘退出）、#9（学习与动态支援）；不新开 Issue，不由单次试点新增通用规范
- **后续**：澄清软件工作流中讨论→行动的非对称边界和角色相关评价；增加覆盖“讨论可交融≠授权编码”“预约完成≠复盘完成”“人/AI 不用同一评价对象”的行为回归。SAP 联调、编译/测试结果及新用户表现不在本记录证据范围内

## 2026-08-15

### IF-073 知情参与者试点：规范价值与执行保障缺口

- **场景**：在 Cursor 使用当前协作 Skill 完成 IF-073 多阶段开发与复盘；人持续核对顾问/设计书原始口径、纠正字段路径和审查输入，并多次提醒 AI 恢复实施讨论深度、学习约定、文档当前性与阶段纪律
- **发现**：本次对规范的诊断与纠偏价值形成了较强证据，但任务最终被救回不能直接证明 Skill 能可靠兑现规范。人的领域判断与风险裁决不可替代；提醒 AI 遵守已知规则、维护状态和证据一致性则是补偿性劳动，必须分账。此前用 Skill 包结构审查回答运行保障是否充分，属于把载体质量当成执行效果的类别错误
- **状态**：`insight` → [知情参与者救回的成功不能替代执行保障](../docs/research/assurance/evidence-synthesis/expert-supervised-pilot-and-assurance-gap.md)
- **后续**：本轮不设计保障系统、不改规范正文。后续另立任务定义保障对象、失效模型与最小验收，再选择技术；新用户表现、无 Skill 反事实和跨任务迁移仍未知

### 上游审查未完成便推进保障设计，纠偏后静默改判

- **场景**：讨论 IF-073 后续方向时，人带来“先审查现有规范、再派生保障”的建议并希望共同讨论；AI 仅凭有限抽查便弱化审查优先级，转问保障系统应保护什么。人明确拉回仓库内容审查后，AI 才发现真实分类与治理问题，却未主动结算新证据如何修正第一轮判断
- **发现**：AI 混淆了路线优先级、重构范围与仓库事实，以技术连续性替代当前认知顺序；最终较正确不等于首次通过。本次应记为 `recovered`，人的议程纠正与证据纠偏属于补偿性劳动。实质改变判断时须显式说明“原判断 → 新证据 → 修正结论 → 保留部分 / 仍未知”，不能静默把旧判断洗成从未发生
- **状态**：`issue` → https://github.com/xge-Hugh/guide-human-ai-collaboration/issues/10
- **后续**：增加覆盖“未验证上游前提便推进下游 + 纠偏后未结算判断修正”的行为回归；本 Issue 不决定规范分类方案，也不预选保障技术

### 跨对话学习层与伴随式导师（候选试点）

- **场景**：两次真实开发中，学习都要由人主动开启；AI 临时选择的插槽一度过浅，而高价值学习实际分布在需求冲突、Lookup 证据、实施落点、审查裁决、对象副作用和复盘纠错等不同阶段

- **状态**：`insight + issue` → [跨对话学习层与伴随式导师候选](../insights/2026-08-13-cross-conversation-learning-layer.md) · [Issue #9](https://github.com/xge-Hugh/guide-human-ai-collaboration/issues/9)

### 主动挑战补回被代理压缩的认知接触面

- **场景**：Cursor 实施讨论中，人从通用质疑继续提出 Fetch join、跨基础设施反事实，并纠正 AI 将“少一层封装”直接等同于“更清晰”的判断；最终方案仍采用 QE
- **发现**：代理仍压缩了仓库操作与环境反馈，但人通过自行生成反例、改变比较前提和纠正抽象判断，扩大了认知与决策接触面；因此“有效接触面”需区分认知/决策与实践/反馈，对话不必然等于纸上谈兵，通用挑战提示也只能打开入口，不能冒充人的具体判断
- **状态**：`insight` → [行动锚定候选](../insights/2026-08-11-action-grounding.md) · D-060/D-062 的实战证据；不新开 Issue
- **后续**：在真实实施中继续观察是否接上运行反馈与纠偏闭环；不由单例推断能力已经增长或下降

### 阶段名与 next_action / 话术不一致（追问后可纠正）

- **场景**：SUNWARD-CRM `xy-service-order-feedback`；仅 `task.md` + `state.json`；档位 0–4 钉住后 AI 问「要我现在就按这个约定实现吗？」
- **初判**：像要从实施讨论直接跳进代码实施
- **追问后**：人问「下一步要进入什么阶段？」→ AI 改口：下一步是**实施讨论（短轮）**，列出路由切分、覆盖写语义、可选字段、错误语义等应收口项，并给出快速通道选项
- **更准的发现**：未必是故意跳阶段；更像 **`next_action` 与收尾问法写成了「开写」**，与 `phase: implementation_discussion` 打架。人一校准，议程能拉回。残留风险：若不追问，人可能把「要实现吗」当成阶段已退出；恢复时只看 state 也会被 `next_action` 误导
- **状态**：`issue` → https://github.com/xge-Hugh/guide-human-ai-collaboration/issues/3
- **后续**：Skill 要求 `next_action` 与 `phase` 同层；收尾问的是本阶段要定的点，不是「现在实现吗」（除非已切 phase 或明示快速通道）

### 实施讨论变成「完整方案审查」（#2 同构）

- **场景**：同上任务，人说「进入实施讨论」后，AI 直接给出心智模型图、落点表、写入规则表，再问「整套默认是否直接采用？」+ 一个 SN 不一致分支；点头后进代码实施
- **发现**：名义上实施讨论，形态却是**实施审查**：人缺思考脚手架时易沦为点头机器。初学者确难独立设计，但若只能点头，也很难独立审查。与 #2 同构——AI 跨过建构门槛后请人裁定终表；不是「给默认就一定错」，缺的是参与设计的路径
- **状态**：`issue` → 并入 https://github.com/xge-Hugh/guide-human-ai-collaboration/issues/2（现场例，非新概念）
- **后续**：规范/Skill 区分「可纠正的默认草案」与「须先激活人模型的承重设计」；实施讨论应保留预测/比较/脚手架，而非默认终案勾选

### 人类脚手架审查：切片中断、学习未邀约、复盘误绑 learning_mode

- **场景**：`xy-service-order-feedback` 人审、AI 辅助；已开切片 1/3，人说基本逻辑无问题并结审查后，AI 跳过切片 2/3；又以「学习模式未开，复盘可跳过」收口，全程未说明如何开启学习模式
- **发现**：
  1. 切片计划中断时至少应提一句或请人确认是否还要看剩余切片（中等问题）
  2. 仅靠 AI 自维阶段易跳步/遗失，缺有力保障（与保障形态议题相关）
  3. **严重**：`learning_mode: off` ≠ 跳过复盘。复盘可为发现协作/流程薄弱点，不必等于能力学习；Skill 参考写的是默认短复盘，学习模式主要约束能力证据结算。把二者绑死是错误
  4. 全程未给人选择/说明如何开学习模式，用户甚至不知道入口
- **状态**：`issue` → https://github.com/xge-Hugh/guide-human-ai-collaboration/issues/4
- **后续**：改正「复盘↔学习模式」语义；审查脚手架中断需确认；学习模式可发现/可切换

### 审查切片：静默跳片无人察觉；短答≠未思考；人也会忘下一步

- **场景**：同上；事后回顾才发现跳过切片 2/3，fork 索要「给我切片2」才补全；切片 1 中人追问写入语义后继续
- **发现**：
  1. **Fork 不是可接受成本**——人当时未感知跳片，回顾才发现；无感知跳阶段是明确风险；软提示下议程自维不稳（计划可丢）再次印证
  2. 分片 +「不变量→路径→代码→例子→风险→一问」能支撑理解；人曾有「是否勿覆盖 new_snid」等想法，权衡后接受——短答可含真实思考；强迫审查模板会过重
  3. **人的工作记忆也会丢掉「还剩切片」**——追问时未必是 AI 忘了下一步，人也可能忘了计划；共同下一步需外置，不能只靠对话瞬时记忆。侧栏/side chat 等也是追问形态选项
- **状态**：`issue` → 评论挂 #4与 #1
- **后续**：审查计划如何外置可恢复；跳片须人可察觉；保持轻脚手架、拒重模板

### 实施讨论：粗骨架有价值，但过早闭合 + 点头关闸
